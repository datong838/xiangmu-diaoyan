# MES 连库方式 — 最终结论（实测）

- 结论时间：2026-10-07 18:00
- 方式：纯只读被动监听（`MES_Watch2.ps1` 每 0.2s 采样，含 TIME_WAIT/CLOSE_WAIT）+ 连通性验证

---

## 一句话结论

**MES 是三层（C/S）架构：客户端只连接应用服务器，不直连数据库。**

```
本机(XDAPP.exe / loadApp.exe)
        │  TCP  →  121.237.178.165 : 55310        ← 实测 ESTABLISHED，端口可达
        ▼
   应用服务器（AnyiMRP 服务端）
        │  （数据库在服务端那一侧，对本机不可见）
        ▼
   数据库 (配置指向 192.168.1.197)  ← 本机不可达，客户端从不直连
```

**对应你图里的判断表 → 命中【场景 B】。**

---

## 实测证据

### 1. 抓到的真实连接（监听脚本，2026-10-07 17:56）

```
[17:56:13] loadApp pid=6112  :: 192.168.8.80:13372 -> 121.237.178.165:55310  ESTABLISHED
[17:56:13] XDAPP   pid=10196 :: 192.168.8.80:13373 -> 121.237.178.165:55310  ESTABLISHED
[17:56:14] XDAPP   pid=10196 :: 192.168.8.80:13374 -> 121.237.178.165:55310  ESTABLISHED
```

- 连接双方是 MES 客户端**两个进程**：`XDAPP.exe` 与 `loadApp.exe`；
- 目标是应用服务器 **`121.237.178.165:55310`**（端口 55310，非 211/1433）；
- 并伴随多条 **TIME_WAIT**，说明是**频繁的短连接**（用时建、用完断）。

### 2. 端口可达性验证

| 目标 | 结果 |
|---|---|
| `121.237.178.165:55310` | ✅ **OPEN**（3 秒内握手成功） |
| `192.168.1.197:1433` | ❌ 不可达 |

### 3. 为什么之前"探不到"

- 早先端口探测只试了 `211/212/1433/3306/1521/5432/80/443/8080` —— **恰好漏掉了真正的 `55310`**，故全部报 closed；
- `ping` 全丢包是**假象**：该主机**禁 ICMP**，但 **TCP 55310 是通的**（ping 不通 ≠ 服务不在）；
- 最初看到的 `XDAPP pid=24548` 是**旧实例**；你登录时客户端重启，**真实实例是 `pid=10196`**，之前那个自然没有连接。

---

## 对"登入数据库"的影响

- 从**本机**无法直连 MES 数据库：客户端根本不建立数据库连接（三层架构），数据库 `192.168.1.197` 对本机不可达。
- 想拿到库表结构 / 直接查库，只有两条路：
  1. **进应用服务器**（`121.237.178.165`，或能访问 `192.168.1.197` 的内网机器）上，用其本地环境连库；
  2. 找 **MES 厂商（Anyi）** 申请开放数据库访问权限/只读账号。
- 客户端配置里的 `mrp_sa / f12345609` 是**应用账号**，用于登录 MES 客户端，未必是数据库账号。
