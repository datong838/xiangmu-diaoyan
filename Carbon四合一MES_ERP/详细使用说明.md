## 1. 一分钟理解这个仓库

**结论：这是一个 pnpm + Turborepo 的 monorepo，内部装了 3 类产品**——不是单一项目。

| 层 | 目录 | 技术 | 角色 |
| --- | --- | --- | --- |
| 应用 | `apps/` | React Router 7 + Vite + TS | ERP / MES 前端 + Rust 几何服务 + 训练/示例 |
| 共享包 | `packages/` | TypeScript（28 个 `@carbon/*`） | 数据库、API 契约、认证、MRP、作业、UI 等 |
| 几何服务 | `crates/` | Rust（7 个 crate） | STEP→GLB、装配运动规划、碰撞检测 |
| 文档站 | `docs/` | Next.js + Fumadocs | docs.carbon.ms 源码 |

**它到底是什么**：把 **ERP + MRP + MES + QMS** 四个传统上各自独立、各用一套数据库的系统，**压进同一个 Postgres 数据库 schema**。工程、计划、生产、质量、财务写的是同一份数据，中间没有一堆同步作业。官方定位是 NetSuite / Epicor / SAP Business One / Plex / Odoo / ERPNext 的开源替代，主攻**复杂装配、代工、按配置下单、高品种小批量**这类通用 ERP 容易卡壳的场景。

**一句话**：Carbon = 一套 Postgres schema + 一套 React 前端 + 一组 Rust 几何服务，把制造全链路（报价→订单→工单→质检→开票→追溯）收拢到可查询、可拥有、可扩展的数据库里，再用 REST API 与 MCP 把整套运营开放出来。

## 3. 架构总览（权威，来自 README + `pnpm-workspace.yaml` catalog）

### 3.1 数据下沉到数据库

官方架构主线：车间（shop floor）、办公室、客户分别访问 **MES** 和 **ERP**；MES/ERP 读写**同一个 Postgres**；一次写入发生时，事件进入 **Inngest** 排队，Inngest 再回调 ERP 执行后台任务。**权限（RLS）、计算合计、变更事件都住在 Postgres**，应用只是它的入口。

### 3.2 关键技术决策（✅ 源码证实）

- **类型三方共享**：数据库 schema → 生成 TS 类型 → 应用、API、MCP 共用一份（`pnpm db:types` 由 `scripts/generate-db-types.ts` 生成）。
- **操作即 Postgres 函数**：制造操作（如创建订单、过账、发料）在数据库层以 RPC 函数实现，再被应用/API/MCP 暴露为带校验、带依赖图、带权限的操作。
- **权限模型**：Postgres **行级安全（RLS）** 做租户隔离；RBAC + ABAC；员工/客户/供应商三种身份同一套权限，APP/API/MCP 三处一致。
- **实时**：Postgres 实时订阅（realtime）。
- **后台**：Inngest 事件队列（非应用内堆重活）。

### 3.4 一个必须讲清的认知（避免旧 README 误导）

> 旧版 README 把数据库层写成 **"Supabase"**（Remix + Supabase + Upstash + Trigger.dev 那套）。当前仓库里**确实有 Supabase 开源组件**：`packages/database/supabase/migrations`（**1092 个**迁移）、`@supabase/postgrest-js`、`@supabase/storage-js`，以及 `crbn up` 拉起的 **GoTrue（auth）/ Storage / Realtime / PostgREST**。
> **所以"Supabase"和"Postgres+PostgREST"说的是同一套东西**——只是现在是**自托管 Docker 镜像**，不再是 Supabase 云服务。新架构描述（Postgres + PostgREST + Kysely）更准确，旧 README 的"Supabase 云"表述已过时。

## 5. 各模块详解

### 5.1 核心业务模块（ERP/MRP/MES/QMS…）

按 README「Features」表，系统覆盖以下业务域（✅ 官方特性表）：

| 模块 | 覆盖能力 |
| --- | --- |
| **ERP — 库存与成本** | 报价、销售订单、采购、库存、开票、实际作业成本（一条记录从报价走到回款） |
| **MRP — 计划** | 需求/供给计划、版本化 BOM 与工艺路线、有限产能排程（引擎在 `@carbon/planning`） |
| **MES — 执行** | 数字工单（traveler）、操作终端、3D 装配说明、扫码、工时采集 |
| **QMS — 质量** | 检验、FAI（首件检验）、不合格（nonconformance）、CAPA、校准、风险管理 |
| **追溯** | 批次/序列号正向反向谱系 |
| **工程** | 多层级 BOM、版本、变更单（ECO）、替代（supersession）、产品配置规则 |
| **会计** | 总账、日记账、多主体、多币种、会计集成 |
| **工作流** | 规则驱动的自动化（触发器/动作/运行历史） |
| **维护与资产** | 计划维护、固定资产、看板补货 |
| **API/Webhooks/MCP** | 类型化 REST 操作、事件 Webhook、权限感知 MCP server |
| **自定义字段** | 不改核心 schema 即可扩展记录 |
| **集成** | Onshape、SolidWorks、Paperless Parts、Linear、Jira、Slack、Ramp、Stripe、Zebra |

### 5.2 数据库与迁移（`@carbon/database`）

- **迁移数量：1092 个**（✅ `ls packages/database/supabase/migrations | wc -l`）——schema 极其成熟，全部以 Supabase 迁移形式维护。
- **生成类型**：`pnpm db:types` → `scripts/generate-db-types.ts`，产出全仓共享的 DB 类型。
- **演示数据集（4 个，✅ 源码证实目录名）**：`satellite` / `robotics` / `precision` / `motor`，位于 `packages/database/src/datasets/data/`。
- **Seed**：`pnpm db:seed:dev -- --email <账号> --dataset <key>`。

### 5.3 API 与 MCP（`@carbon/api` + `scripts/generate-mcp.ts`）

- API 暴露的是"与应用相同的制造操作"，每个操作**校验输入、更新依赖记录、强制当前身份权限**。
- 两个入口、同一套参数：
  - **HTTP**：`POST /api/v1/{module}/{operation}`，带公开 OpenAPI spec，可生成任意语言 typed 客户端。
  - **MCP server**：作为 AI agent 的工具，权限跟随 API Key 或登录用户。
- **模块数（✅ 源码证实）**：`.claude/rules/mcp-tools-reference.md` 与 `scripts/lib/validator-loader.ts` 均确认 **15 个模块**（"15/15 modules load, 406 validators found"）。
- 🌐 **官网规模数字（未本地验证）**：官网宣称 "381 resources / 1,641 endpoints" 与 "1,374 operations across 15 modules"。这些数字来自**生成式 manifest**（运行 `pnpm generate:mcp` 后才会落到 `tool-metadata.json`），本次未执行生成，故未本地核对；引用时请标注"官网宣称"。

### 5.4 企业版（`@carbon/ee`，商业许可）

目录探查（✅）：`accounting`(xero/quickbooks)、`linear`、`onshape`、`workflows`、`mcp`、`email-notifications`、`integrations`、`sso`、`jira`、`audit`、`spend`、`slack`。

> ⚠️ **许可边界（open core）**：整个仓库是 **AGPL-3.0**；但 `packages/ee` 与文件名带 `.ee.` 的文件走 **Carbon Commercial License**。API Key 与 MCP 含在 Business/Enterprise 计划，自托管商用需商业许可。选前进前务必读 `LICENSE` 与官网计划页。

## 6. 本地开发全流程（✅ 权威，来自当前 README）

### 6.1 最简启动（推荐先跑通这条）

```bash
git clone https://github.com/crbnos/carbon.git
cd carbon
corepack enable && pnpm install
cp .env.example .env          # 只需填真正的密钥；端口/URL/密钥由 crbn up 自动写入 .env.local
pnpm dev                      # = crbn up --no-portless
```

`pnpm dev` 会：拉起 Docker 全栈（Postgres、PostgREST、GoTrue(auth)、Storage、Realtime、Inngest、Redis、邮件捕获器）→ 应用迁移 → 生成类型 → 启动应用。

### 6.2 启动后入口

| 界面 | 地址 |
| --- | --- |
| ERP | http://localhost:3000 |
| MES | http://localhost:3001 |
| API（PostgREST 风格） | http://localhost:54321 |

- **默认账号**：`test@carbon.ms`（dev 栈会自动 seed 该用户并跳过 magic link 验证）。
- **灌入演示数据**（二选一数据集）：
  ```bash
  pnpm db:seed:dev -- --email test@carbon.ms --dataset satellite
  # 可选：robotics | precision | motor
  ```
- **无需任何外部账号**即可本地运行。Email / Google/Microsoft 登录 / Stripe / PostHog / AI 提供方均可在 `.env` 中留空（可选配置）。

### 6.3 常用命令速查（✅ 来自 README + 根 package.json）

## 7. `crbn` 开发 CLI 完整参考（✅ 来自 `packages/dev/bin/crbn` 与 `src/commands/`）

`crbn` 是 Bash 路由器：`checkout` 用 bash（需在父 shell 改目录），其余委托 `tsx packages/dev/src/main.ts`（citty 框架）。**安装一次即可**：
```bash
./setup.sh            # 安装（写入 PATH + crbn() 函数）
source ./setup.sh     # 安装并立即在当前 shell 激活
```
`bin/crbn` 强制 **Node 22+**（低于即报错退出）。

**子命令（✅ 枚举自 `packages/dev/src/commands/`）**：

| 子命令 | 作用 |
| --- | --- |
| `crbn up [--no-portless]` | 启动本 worktree 的 Docker 栈 + 应用（`pnpm dev` 即 `crbn up --no-portless`） |
| `crbn down` | 停止栈 |
| `crbn status` | 端口与健康检查 |
| `crbn reset` | 擦除并重启 |
| `crbn checkout -b <分支>` | 新建分支 + worktree（脱离 HEAD） |
| `crbn checkout <PR号>` | 把某 PR 检出到独立 worktree |
| `crbn restore <backup>` | 恢复生产快照（`.backup`/`.dump`；默认脱敏邮箱为 `@example.test`） |
| `crbn init / new / copy / list / reload / remove / migrate` | 初始化、新建、复制、列出、重载、移除、迁移等 |

**worktree 隔离**：每个 git worktree 拥有**独立栈**，各自跑在 HTTPS `.dev` 域名（portless），可多分支并行开发——这对你"多 worker 并行开发"的工作流尤其契合。

### 10.3 本机特有坑（WorkBuddy 沙箱 fs-shim 拦截 pnpm）

**症状**：`pnpm install` 跑到 symlink/link 阶段报 `ERR_PNPM_CODEBUDDY_BROKER_DENY … [symlinkAllModules] EEXIST/ENOENT` 或 `crbn up` 的 `mutateModules` 报 `CODEBUDDY_BROKER_DENY EEXIST: symlink …`。

**根因**：WorkBuddy 沙箱向 shell 注入 `NODE_OPTIONS=--require=…/node-language-shim.cjs` 与 `BASH_ENV=…/brokered-sandbox-bash-env.sh`，其 node fs-shim 会代理/拦截 symlink，把 pnpm 的 `forceSymlink` 误判为越权而 deny。**这不是 Carbon 的问题，也不是权限问题。**

**解法（实测有效，2026-10-04）**：用 `env -i` 彻底丢弃注入变量，仅保留干净 node PATH 运行真 pnpm：

```bash
# 1) 杀掉卡死的 install（必要时清掉 store 里指向本仓库的陈旧项目 symlink）
rm -f ~/Library/pnpm/store/v10/projects/<hash>   # 仅当报 EEXIST 且目标指向本仓库时

# 2) 干净环境重跑（镜像源用 npmmirror，直连即可）
cd /path/to/mes_erp/carbon
env -i HOME=$HOME \
  PATH="/Users/ddt/.workbuddy/binaries/node/versions/22.22.2-2/bin:/usr/bin:/bin:/usr/sbin:/sbin" \
  COREPACK_ENABLE_DOWNLOAD_PROMPT=0 \
  /Users/ddt/.workbuddy/binaries/node/versions/22.22.2-2/bin/node \
  /Volumes/NVME2T/.cache/node/corepack/v1/pnpm/10.33.4/dist/pnpm.cjs install \
  --registry=https://registry.npmmirror.com --prefer-offline

# 3) 任何会 spawn node 的 Carbon 命令（crbn up / build / tsc）同理包 env -i
```

> 关键：单纯 `dangerouslyDisableSandbox: true` 不够——shim 是从环境变量加载的，必须 `env -i` 清掉 `NODE_OPTIONS`/`BASH_ENV`/`CODEBUDDY_*` 才会消失。受管 node 二进制本身是干净的 Mach-O，未被包装。
