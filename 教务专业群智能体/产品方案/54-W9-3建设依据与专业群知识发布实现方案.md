# W9-3 建设依据与专业群知识发布实现方案

> 版本：v1.0　日期：2026-10-18　状态：编码基线。  
> 对应波次：W9-3。  
> 对应任务：T01、T03、T05，并为 T02、T04 提供知识底座。  
> 本波限制：只使用合成资料，不调用外部智能能力，不接入学校真实数据。

## 1. 本波要解决的问题

W9-2 已经能够保存学校控制的材料原件和材料版本，但“有文件”还不是“有可用建设知识”。W9-3 要证明一条受控链路：

```text
申报书 / 建设任务书 / 实施方案的材料版本
  → 登记为建设依据版本
  → 拆成带原文位置的候选条款
  → 建立建设要求和候选关系
  → 负责人逐项确认、拒绝或登记冲突
  → 把已确认内容发布为正式知识版本
  → 在当前专业群范围内检索并回到原文件位置
```

这条链首先实现 T05；材料来源和可继续补充能力承接 T01；所有对象显式携带学校、专业群和建设周期范围，后续可连接 T03 已确认的专业关系。它不直接计算指标，不把任务完成改成指标达成，也不生成正式申报材料。

## 2. 产品对象与边界

| 对象 | 作用 | 关键约束 |
| --- | --- | --- |
| 建设依据 | 表示申报书、建设任务书或实施方案 | 必须引用当前范围内已存在的材料版本 |
| 依据版本 | 固定材料版本、批准状态和适用周期 | 换版新增版本，不覆盖旧版本 |
| 原文条款 | 保存条款类型、原文位置、原文摘录和整理表述 | 原文位置和摘录不可丢失；初始状态为候选 |
| 建设要求 | 表示目标、指标、任务、节点或支撑要求 | 本波只形成要求，不执行指标计算 |
| 候选关系 | 连接条款和建设要求 | 规则或人员均只能先提出候选 |
| 人工决定 | 接受、修改后接受、拒绝或保留冲突 | 必须记录决定人、理由和时间 |
| 冲突 | 并列保存不同来源的目标值、时间、责任或材料要求 | 系统不得自动裁决 |
| 知识发布 | 固定本次进入正式知识范围的确认关系 | 只有已确认关系可发布；发布后仍能回到条款和材料版本 |
| 正式知识条目 | 为检索、任务和后续报告提供稳定输入 | 只读取已发布版本，候选内容不得混入 |

## 3. 权限设计

- 教师可以检索本专业群已发布知识，但不能登记依据、确认候选或发布知识。
- 专业群负责人可以登记依据、录入候选条款与建设要求、处理候选关系、登记和解决冲突、发布知识。
- 教务审核人员可以查看依据和候选关系、检索已发布知识；本切片不赋予其替负责人发布的权限。
- 信息支持人员只查看不含业务标题、正文、数量和命中词的系统运行状态。
- 直接使用其他学校、其他专业群或其他周期对象编号时统一返回“不可访问”，不暴露对象是否存在。

## 4. 数据设计

### 4.1 建设依据与版本

`basis_documents` 保存稳定编号、类型、范围、当前版本和状态。`basis_document_versions` 保存所引用的 `material_version_id`、批准状态、适用起止日期、版本号、变更原因和内容摘要。

同一个材料版本可以登记成一种依据，但不能跨范围引用。正式依据必须由负责人登记；草稿、待批准、已批准和已失效状态明确区分。

### 4.2 条款、要求和候选关系

`basis_clauses` 保存稳定条款编号；`basis_clause_versions` 追加保存：

- 依据版本；
- 条款类型；
- 页码、章节、表格、行列或段落等原文位置；
- 原文摘录及校验值；
- 整理后的陈述；
- 候选状态和建立人。

`construction_requirements` 与其版本保存目标、指标、任务、节点和支撑要求。`knowledge_relation_candidates` 保存条款版本与要求版本之间的候选关系、提出方式、理由、状态和人工决定。

### 4.3 冲突与正式知识

`basis_conflicts` 并列保存两个条款版本及影响说明；`basis_decisions` 追加保存处理决定，不修改原条款。

`knowledge_releases` 表示一次知识发布；`knowledge_entries` 保存发布产生的正式知识条目。条目固定条款版本、建设要求版本、候选关系和发布版本。正式检索只查询已发布且未失效的知识条目。

## 5. 接口切片

| 接口 | 用途 | 人工控制点 |
| --- | --- | --- |
| `POST /basis-documents` | 将一个材料版本登记为三类依据之一 | 负责人明确批准状态和适用周期 |
| `GET /basis-documents` | 查看当前范围的依据目录 | 按角色和范围过滤 |
| `POST /basis-documents/{id}/clauses` | 新增候选条款、建设要求及其候选关系 | 只产生候选，不进入正式知识 |
| `GET /knowledge-candidates` | 查看待确认、已确认、已拒绝候选 | 不与正式知识结果混合 |
| `POST /knowledge-candidates/{id}/decisions` | 接受或拒绝候选 | 必须由获授权人员给出理由 |
| `POST /basis-conflicts` | 登记两处来源冲突 | 冲突保持未解决状态 |
| `POST /basis-conflicts/{id}/decisions` | 保存采用、并列保留或待补材料的口径决定 | 不改写两个来源原文 |
| `POST /knowledge-releases` | 发布一批已确认候选 | 固定输入版本并产生发布回执 |
| `GET /knowledge/search` | 检索已发布正式知识 | 返回条款、要求和材料版本追溯信息 |

所有写接口使用统一写入信封，带范围、`expectedVersionId`、幂等键、目的、操作者和人工决定；业务写入、建设账本和 Outbox 在同一事务提交。

## 6. 首个合成验收链

1. 在 DEMO-G01 建立申报书、建设任务书和实施方案三个合成材料及版本。
2. 负责人分别登记三类依据，并保留批准状态与适用周期。
3. 从建设任务书表格第 3 行录入“2026 年新增合作企业 3 家”候选指标条款。
4. 同时建立一个“指标”建设要求及“条款定义要求”候选关系。
5. 未确认前搜索正式知识，命中数为 0。
6. 负责人确认候选关系并记录理由；仍未发布时正式搜索命中数为 0。
7. 负责人发布知识版本，搜索命中并能回查材料版本、条款位置和确认决定。
8. 在实施方案中录入目标值不同的条款，登记冲突；正式搜索不自动替换已发布口径。
9. 另一专业群、信息支持人员和无权限身份搜索时均不泄露标题、数量、摘要和命中词。
10. 重复请求返回同一回执；旧版本或不同请求复用幂等键被拒绝；每次写入均可在建设账本中回查。

## 7. 本波实现顺序

### W9-3A：结构化可信链

建立上述表、约束、角色能力、写接口、正式知识检索和合成集成测试。这是本次编码范围。

### W9-3B：资料拆解办理

增加拆解批次、读取状态、页表段落拆解、待补项和批量确认页面所需接口。输入仍可由确定性夹具产生，不以模型输出作为事实。

### W9-3C：全文、关系与向量组合检索

先验证 PostgreSQL 全文与关系检索；向量检索必须在学校批准样例、嵌入模型边界和索引恢复方案明确后启用。任何检索方式都共享同一范围过滤和正式知识门槛。

## 8. 自测与通过门槛

- 数据库迁移可在空库重复执行，跨范围外键被数据库或服务拒绝。
- 三类依据均固定到材料版本；材料换版不静默替换依据版本。
- 候选确认前、确认后未发布、发布后三种检索结果清楚区分。
- 正式知识可沿“知识条目—候选关系—条款版本—依据版本—材料版本”完整回查。
- 冲突不自动裁决，解决决定不删除另一来源。
- 教师、负责人、审核人、信息支持人员完成允许和拒绝用例。
- 跨学校、跨专业群、跨周期搜索和直接编号访问均为零泄露。
- 幂等、旧版本、并发写入、账本和 Outbox 通过运行测试。
- OpenAPI、实现状态、测试、验证记录与本方案保持一致。

## 9. 风险和后续事项

- 本切片的条款由合成请求录入，只证明产品写入和确认链，不证明真实文档解析质量。
- 首期正式检索采用确定性文本匹配，不宣称语义检索或问答完成。
- 目标、指标和任务在本波只是知识对象；指标计算、任务闭环和差距整改属于 W9-4。
- 真实身份、对象存储、备份平台、学校部署位置和批准样例仍须在学校环境单独验证。
