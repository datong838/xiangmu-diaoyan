# W9 数据模型、关系、版本与建设账本技术方案

> 版本：v1.0　日期：2026-10-18　状态：历史技术初稿，未经正式组织评审；作为第 122—128 份评审稿的详细参考。  
> 对应方案：13、14、20、23、38。  
> 文档职责：把产品对象、关系、状态和追加式建设账本转换为数据库可实现约束。

## 1. 数据建模原则

1. 稳定对象编号与可变版本分离；改名、移动或修订不改变对象编号。
2. 当前版本只是指针，历史版本不可覆盖。
3. 对象关系是一等数据，不能只藏在报告文字或智能体回答中。
4. 候选关系、人工确认关系、计算结果和正式结论使用不同记录类型。
5. 每条业务数据必须带学校、专业群、建设周期和可见范围；校级对象也要显式说明范围。
6. 所有写操作与建设账本在同一数据库事务中提交。
7. 删除默认采用停用或归档；涉及原件、审核、指标和正式成果的记录不提供普通物理删除。

## 2. 公共标识和范围键

所有核心表使用不可读、不可猜测的稳定标识。业务显示编号另设字段。

| 字段 | 用途 |
| --- | --- |
| `id` | 稳定主键 |
| `school_id` | 学校范围；所有业务查询首个过滤条件 |
| `group_id` | 专业群范围；校级对象可为空但必须有范围类型 |
| `cycle_id` | 建设周期 |
| `object_code` | 对用户显示的稳定编号，如 `IND-2026-001` |
| `current_version_id` | 当前采用版本指针 |
| `status` | 当前业务状态，不替代版本内容 |
| `visibility_policy_id` | 可见范围规则 |
| `created_by/created_at` | 建立人和时间 |

数据库主键、唯一约束和外键必须包含或校验 `school_id`，禁止只凭对象编号跨学校连接。

## 3. 核心表组

### 3.1 范围与组织

- `schools`
- `departments`
- `professional_groups`
- `professions`
- `group_profession_relations`
- `construction_cycles`
- `people`
- `role_assignments`
- `responsibility_assignments`

`group_profession_relations` 记录核心专业、支撑专业、有效期和确认人。一个专业可以在获准情况下参与多个专业群，但关系和权限分别保存。

### 3.2 依据、目标与指标

- `basis_documents`
- `basis_document_versions`
- `basis_clauses`
- `basis_clause_versions`
- `basis_conflicts`
- `basis_decisions`
- `construction_items`
- `objectives`
- `indicators`
- `indicator_rule_versions`
- `indicator_evidence_requirements`

三类文件是三个对象，各自有版本。条款引用必须保存文件版本、章节或表格位置和原文片段校验值。冲突通过 `basis_conflicts` 并列来源，通过 `basis_decisions` 保存人工决定和适用时间。

### 3.3 计划、任务和日常工作

- `plans`
- `plan_versions`
- `tasks`
- `task_versions`
- `task_assignments`
- `task_transitions`
- `work_records`
- `work_record_versions`
- `issues`
- `issue_transitions`

任务状态与指标状态分开。`task_transitions` 记录派发、提交、退回、补充、确认和关闭；任务完成不能直接更新指标事实值。

### 3.4 材料、证据和事实

- `materials`
- `material_versions`
- `material_blobs`
- `material_duplicate_groups`
- `material_usages`
- `facts`
- `fact_versions`
- `evidence_links`
- `achievement_candidates`
- `classification_decisions`

文件原件的对象存储键、大小、媒体类型和校验值保存在 `material_blobs`。材料对象可有多个版本或多个附件。同一协议的扫描件和电子版通过重复组表达，不删除原件，也不重复计数。

### 3.5 指标、进度和差距

- `indicator_evaluation_runs`
- `indicator_evaluation_inputs`
- `indicator_calculated_results`
- `progress_confirmations`
- `gap_items`
- `remediation_tasks`

一次计算运行固定规则版本、截止时间和输入快照。系统计算结果与负责人确认结果分别保存。重新计算新增运行，不覆盖旧结果。

### 3.6 模板与成果

- `templates`
- `template_versions`
- `deliverables`
- `deliverable_versions`
- `deliverable_sections`
- `citations`
- `review_records`
- `export_records`

引用保存来源对象、来源版本、使用位置和引用快照。正式导出必须关联获批准的成果版本、模板版本、审核记录和导出人。

### 3.7 知识与智能体

- `knowledge_entries`
- `knowledge_entry_versions`
- `knowledge_relations`
- `knowledge_index_jobs`
- `agent_tasks`
- `agent_task_steps`
- `agent_context_snapshots`
- `agent_proposals`
- `agent_action_attempts`
- `human_decisions`

知识条目只索引已经允许进入知识范围的对象版本。智能体建议使用 `agent_proposals`，未经确认不能改成正式关系或业务状态。

### 3.8 操作、异常和后台任务

- `ledger_entries`
- `idempotency_records`
- `outbox_events`
- `background_jobs`
- `action_receipts`
- `security_events`
- `backup_manifests`
- `restore_runs`

## 4. 统一版本模型

每类可变对象采用“对象表 + 版本表”模式：

```text
对象
  ├─ 稳定编号、范围、当前状态
  └─ current_version_id

版本
  ├─ version_no
  ├─ content / structured_fields
  ├─ based_on_version_id
  ├─ change_reason
  ├─ author
  ├─ created_at
  └─ content_hash
```

版本建立必须带 `expected_current_version_id`。若提交时当前版本已变化，接口返回版本冲突，不自动合并或覆盖。

## 5. 统一关系模型

固定高频关系使用专表保证外键和业务约束；跨域和可扩展关系使用 `object_relations`：

| 字段 | 含义 |
| --- | --- |
| `relation_type` | 来源于、分解为、负责、支撑、引用、替代、冲突、影响等 |
| `source_type/source_id` | 起点对象 |
| `target_type/target_id` | 终点对象 |
| `source_version_id/target_version_id` | 建立关系时采用的版本 |
| `relation_state` | 候选、已确认、已拒绝、已失效 |
| `valid_from/valid_to` | 有效期 |
| `proposed_by` | 人或智能体 |
| `confirmed_by/confirmed_at` | 人工确认 |
| `reason` | 建立、拒绝或失效原因 |

正式业务查询默认只读取“已确认且当前有效”的关系。候选关系必须单独显示。

## 6. 建设账本

`ledger_entries` 为追加式记录，至少包含：

- 学校、专业群、周期；
- 操作编号和幂等键；
- 操作者类型、操作者编号、代理人关系；
- 动作类型；
- 对象类型和对象编号；
- 操作前版本和操作后版本；
- 输入来源、人工决定和动作回执编号；
- 结果状态：成功、拒绝、冲突、结果未知、已恢复；
- 时间、客户端和必要的脱敏技术信息；
- 前一条账本摘要和当前摘要，用于检查连续性。

账本正文不复制大文件或敏感正文，只记录可回查的对象和版本引用。

## 7. 写操作事务模板

```text
验证身份与范围
  → 锁定对象当前版本
  → 校验 expected_version
  → 校验状态转换与人工决定
  → 检查 idempotency_key
  → 新增对象版本 / 关系 / 状态转换
  → 新增 ledger_entry
  → 新增 outbox_event
  → 提交数据库事务
  → 返回 action_receipt
```

任何一步失败都不提交部分业务结果。外部云动作不与数据库事务混在一起，先得到候选回执，再由学校侧写操作确认落库。

## 8. 必须由数据库或服务强制的约束

1. 不能建立跨学校的对象关系。
2. 不能把其他专业群的对象加入当前知识快照。
3. 未确认候选不能成为指标输入或正式报告事实。
4. 任务完成不能直接更新指标确认值。
5. 同一企业、同一期间、同一成果不能因多个附件重复计数。
6. 已批准成果的新修改必须形成新草稿并重新审核。
7. 无权角色不能通过已知对象编号读取标题、数量或版本信息。
8. 归档原件和正式审核记录不能被普通业务操作物理删除。
9. 结果未知的动作不能用同一业务目的重新生成不同幂等键直接重试。
10. 恢复后必须核对账本连续性和对象当前版本指针。

## 9. 首批迁移和样例数据

首批合成数据只建立：

- DEMO-G01 人工智能专业群及五个专业；
- 2026—2028 建设周期；
- 三类依据及演示版本；
- “2026 年新增合作企业 3 家”指标及规则 v2；
- A—D 企业材料与不同状态；
- B 企业任务 v2、教师提交 v1/v2、退回意见；
- 一份 6 月总结和年度报告章节草稿；
- 四类角色和最小权限；
- NEW-G02 空白专业群，仅包含独立初始化配置。

样例初始化脚本不得包含真实学校资料或真实人员信息。

## 10. 数据层验证

- 对象稳定编号和版本并发冲突；
- 关系候选、确认、拒绝、失效；
- 重复材料不重复计数；
- 跨群外键与查询隔离；
- 每次业务写入都有且只有一条对应账本事务结果；
- 重复幂等键返回同一回执；
- 结果未知后只读核对能够找到已提交或未提交状态；
- 备份恢复后对象、版本、关系、文件校验值和账本摘要一致。

## 11. 当前结论

本方案给出数据库级实现边界和表组。2026-10-18 已按第 46 份方案完成 W9-1 首批范围对象、版本、同校关系、幂等、回执、追加式建设账本和 Outbox 迁移，并通过实际 PostgreSQL 约束验证；任务、材料、指标、成果、知识和智能体表组仍属于后续波次，不能据此宣称本方案全部实现。
