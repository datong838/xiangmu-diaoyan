# 统一对象与功能字段设计差异清单

> 版本：v1.0　日期：2026-10-18　状态：内部评审稿。  
> 对应差距：G004。  
> 对照范围：`专业群AI工作站功能清单与字段设计.md` 与产品方案 01—19。  
> 文档职责：识别既有字段设计哪些可以沿用、哪些需要调整、哪些对象缺失；本文件是下一轮字段文档修订依据，不直接代表数据库已经修改。

## 1. 对照结论

既有字段设计已经覆盖专业群、专业、成员、指标修订、分期目标、工作记录、成果、进展、材料版本、任务、报告、引用、审核、后台作业、对话、权限和审计，能够保留为实现基础。

本轮产品方案扩大了产品设计深度，需要补充七类结构：

1. 三类建设依据及原文条款、建设事项、冲突与口径决定；
2. 通用对象关系和关系确认状态；
3. 专业群智能体任务、处理计划、步骤、待确认动作和写回结果；
4. 资料交接批次、候选对象、候选关系和知识发布；
5. T02 内容整理任务、输出结构、来源快照和缺项；
6. 问题、原因、补充动作和补充任务闭环；
7. 版本变化影响、待复核对象和处理结果。

## 2. 判定标记

| 标记 | 含义 |
| --- | --- |
| 沿用 | 现有对象和关键约束足以承接产品方案 |
| 调整 | 现有对象可保留，但字段、状态或约束需补充 |
| 新增 | 产品方案已经定义，现有字段设计没有独立承载对象 |
| 待确认 | 依赖学校真实口径或实施技术方案，当前不写死 |

## 3. 已覆盖并沿用的对象

| 产品对象 | 现有表或结构 | 结论 | 说明 |
| --- | --- | --- | --- |
| 学校、部门、专业 | `school`、`department`、`major` | 沿用 | 支持学校边界和真实部门树 |
| 专业群 | `major_group` | 调整 | 生命周期状态需与申报期、建设期、验收期及归档规则统一 |
| 核心/支撑专业关系 | `major_group_major` | 沿用 | 已有角色和有效期，可支撑历史关系 |
| 建设周期 | `construction_cycle` | 调整 | 不能只绑定一份任务书材料版本，应关联共同建设依据集合 |
| 用户、身份、角色与授权 | `sys_user`、`user_identity`、`role_assignment` 等 | 沿用 | 运维与业务权限分开设计正确 |
| 指标稳定身份与修订 | `indicator`、`indicator_revision` | 沿用 | 已区分稳定对象和不可覆盖修订 |
| 分期目标与专业分配 | `indicator_period_target`、`indicator_major_allocation` | 沿用 | 支持周期、适用性、联合/独立贡献 |
| 工作记录 | `work_record`、`work_record_material` | 调整 | 需补工作记录内容版本或修订对象 |
| 成果及去重 | `achievement`、`achievement_material` | 沿用 | business_key 需由人确认，不由模型臆造 |
| 进展填报 | `indicator_progress`、`progress_evidence` | 调整 | 需增加独立计算快照和正式判断对象 |
| 材料与不可变版本 | `material`、`material_version` | 沿用 | 符合原件不可覆盖要求 |
| 材料处理与定位 | `material_processing`、`material_chunk` | 调整 | 需从解析扩展到吸收批次和知识发布状态 |
| 材料—指标关系 | `material_indicator` | 沿用 | 已区分建议、确认、拒绝和撤回 |
| 材料—专业关系 | `material_major` | 调整 | 需记录提出方式、确认状态和有效期 |
| 资源授权 | `resource_grant` | 沿用 | 需明确正文、摘要和存在性是否分动作授权 |
| 任务与提交 | `task`、`task_submission` | 调整 | 需补任务来源、父任务、预期产出、调整版本和确认状态 |
| 周期总结与计划 | `periodic_plan` | 调整 | 当前 content 大字段不足以表达事实、差异、遗留和下期任务关系 |
| 业绩分类 | `achievement_classification` | 沿用 | 支持人工确认和规则版本 |
| 新业务事项 | `business_item` | 沿用 | 可承接 T01—T18 外的新事项 |
| 提醒与通知 | `alert_rule`、`alert_event`、`notification` | 沿用 | 已区分提醒与问题解决、失败与未知 |
| 模板与模板版本 | `report_template`、`report_template_version` | 沿用 | 可承接已知和新增最终成品模板 |
| 报告及不可变版本 | `report`、`report_version` | 沿用 | 已分报告容器和版本 |
| 报告引用、审核和导出 | `report_citation`、`review_record`、`report_export` | 调整 | 引用需允许只指向进度快照、事实或材料中的任一类来源 |
| 后台作业 | `async_job` | 沿用 | 与业务任务分开且支持幂等和 unknown |
| 对话与消息 | `conversation`、`conversation_message` | 调整 | 对话不能代替智能体任务单和业务写回记录 |
| 模型与成本 | `model_config`、`model_call`、`budget_policy` | 沿用 | 保持服务能力与学校数据边界 |
| 审计 | `audit_log` | 调整 | 需与产品建设账本区分：审计记录技术操作，建设账本表达业务变化 |

## 4. 必须新增的产品对象

### 4.1 建设依据与口径

| 建议对象 | 核心字段 | 作用 |
| --- | --- | --- |
| `basis_document` | group、cycle、document_type、title、current_version、approval_status、effective_period | 区分申报书、任务书、实施方案及其他依据 |
| `basis_document_version` | document、version_no、material_version、approval_status、approved_at、effective_from/to | 绑定原件版本和批准状态 |
| `source_clause` | document_version、clause_type、text、locator、status | 保存条款、表格行、目标或节点原文定位 |
| `construction_item` | group、cycle、stable_code、name、status | 把多份文件相关要求组织为同一建设事项 |
| `clause_item_relation` | clause、item、relation_type、status、confirmed_by | 保存候选和已确认条款对应关系 |
| `scope_conflict` | subject_type/id、conflict_type、source_manifest、impact_scope、status | 明确文件或规则之间的冲突 |
| `scope_decision` | conflict、decision、reason、effective_scope、confirmed_by/at、supersedes_id | 保存负责人正式口径决定 |

### 4.2 通用关系与确认

现有字段设计大量使用专用关联表，这是正确的；仍需一个受控的通用关系对象承载尚未进入专用表或需要统一追溯的关系：

| 建议对象 | 核心字段 | 约束 |
| --- | --- | --- |
| `object_relation` | source_type/id/version、relation_type、target_type/id/version、origin、status、reason、valid_from/to、confirmed_by/at | relation_type 使用白名单；确认后若有专用业务表，应同步写入并保留本关系追溯 |

它不能替代 `material_indicator` 等强约束专用表，也不能成为任意对象随意关联的万能表。

### 4.3 智能体任务与人机确认

| 建议对象 | 核心字段 | 作用 |
| --- | --- | --- |
| `agent_task` | user、group、cycle、original_request、interpreted_goal、expected_output、status、current_step、writeback_target | 一次办理过程的稳定业务身份 |
| `agent_task_scope` | task、major、period、allowed_actions、knowledge_manifest、permission_snapshot | 固定本次知识范围和权限 |
| `agent_task_step` | task、sequence、capability_code、input_snapshot、status、result_ref、error | 保存九步协议中的可执行步骤 |
| `agent_confirmation` | task、step、confirmation_type、proposed_change、impact_manifest、required_role、status、decided_by/at | 承载接受、修改后接受、拒绝、退回和暂不决定 |
| `agent_writeback` | task、step、target_type/id/version、action、request_id、result、ledger_entry_id | 证明聊天结果实际写回哪个对象 |

### 4.4 知识吸收与发布

| 建议对象 | 核心字段 | 作用 |
| --- | --- | --- |
| `ingestion_batch` | group、purpose、submitted_by、visibility、status、counts、started/finished_at | 管理一次资料交接或批量吸收 |
| `ingestion_item` | batch、material_version、read_status、decompose_status、knowledge_status、error | 逐份显示登记、读取、拆解、待确认和发布状态 |
| `candidate_object` | item、object_type、proposed_payload、source_locator、status、reviewed_by | 承载从资料识别出的候选对象 |
| `knowledge_release` | object_type/id/version、group、scope、confirmed_by/at、release_status | 记录某版本何时进入可用知识范围 |
| `knowledge_issue` | item/object、issue_type、description、status、assignee | 承载冲突、未知、受限、重复和未覆盖 |

### 4.5 内容整理与正式产物前置

| 建议对象 | 核心字段 | 作用 |
| --- | --- | --- |
| `content_transform_task` | group、purpose、audience、output_type、structure_schema、status、owner | T02 的独立办理任务 |
| `content_input_snapshot` | task、source_type/id/version、included_at | 固定本次使用的材料和版本 |
| `content_draft_version` | task、version_no、parent_version、content、source_manifest、change_summary、status | 保存文字、表格结构或汇报内容的每版草稿 |
| `content_gap` | task、section_key、missing_type、description、status | 缺内容时明确留空和补充 |

### 4.6 问题、差距和补充任务

| 建议对象 | 核心字段 | 作用 |
| --- | --- | --- |
| `business_issue` | group、source_type/id、issue_type、description、status、owner、due_at | 表达需要处理的业务问题，不与提醒事件混用 |
| `gap_analysis` | target、calculation_snapshot、gap_type、reason、evidence、status | 区分数量不足、工作未完成、缺证据和口径待确认 |
| `corrective_action` | gap、action_type、proposal、assignee_suggestion、due_suggestion、status | 智能体提出的补工作、补材料或核实建议 |
| `corrective_task_relation` | action、task、confirmed_by/at | 负责人确认后与正式任务关联 |

### 4.7 版本影响复核

| 建议对象 | 核心字段 | 作用 |
| --- | --- | --- |
| `change_impact_batch` | changed_type/id/version、previous_version、detected_at、status | 一次版本变化的影响分析批次 |
| `change_impact_item` | batch、affected_type/id/version、impact_type、suggestion、status、reviewed_by/at、resolution | 逐项决定继续沿用、重算、重写或不受影响 |

## 5. 必须调整的现有结构

### 5.1 `construction_cycle`

取消“生效时任务书依据必填”的单一文件假设，改为通过建设依据关系指向经确认的申报书、任务书、实施方案或口径决定集合。

### 5.2 `work_record`

新增稳定身份与内容版本，或增加 `work_record_revision`。被退回后修改和已确认后纠错不能覆盖原内容。

### 5.3 `indicator_progress`

保留进展填报，但新增：

- `progress_calculation_snapshot`：规则版本、截止点、输入事实、去重明细、计算结果；
- `progress_judgement`：系统建议状态、人工正式结论、确认人和失效关系。

避免一个表同时承担填报、计算和正式结论。

### 5.4 `task`

补充 `source_type/source_id`、`parent_task_id`、`expected_output`、`confirmation_status`、`adjustment_revision` 和 `assigned_by`。负责人确认后派发与执行人提交应分开。

### 5.5 `periodic_plan`

拆出周期总结版本、事实引用、计划差异、遗留事项和下期任务关系。`content` 只保存最终可读内容，不能替代结构化关系。

### 5.6 `report_citation`

允许引用事实、成果、进度计算、材料版本、条款或口径决定。约束改为“至少一种来源必填”，不能要求所有汇总数字同时具备单一 `material_version_id`。

### 5.7 `conversation`

增加与 `agent_task` 的关系。聊天消息只保存交流，智能体任务保存办理状态，业务对象保存正式结果。

### 5.8 `audit_log`

新增 `business_ledger_entry` 或明确另一套建设账本：

- `audit_log`：谁调用了什么功能、结果怎样；
- 建设账本：业务对象从什么状态和版本变为什么、依据和影响是什么。

二者通过 request_id、agent_task_id 或 ledger_entry_id 关联。

## 6. 状态对齐

| 产品概念 | 现有状态 | 调整要求 |
| --- | --- | --- |
| 任务 | todo/doing/submitted/done/cancelled | 增加草稿、待确认、待验收、被退回，或用独立确认状态表达 |
| 工作记录 | draft/submitted/confirmed/returned | 补作废、替代及内容版本 |
| 材料解析 | pending/processing/succeeded/failed/unsupported | 产品显示“可读取/部分可读/无法读取”；技术状态与产品状态映射 |
| 证据关系 | suggested/confirmed/rejected/withdrawn | 与 13 文档候选、待补充、已确认、被拒绝、已失效对齐 |
| 报告 | draft/reviewing/returned/approved/invalidated/archived | 保留；编制任务另需准备中、资料不足、编写中状态 |
| 后台作业 | queued/running/succeeded/failed/cancel_requested/cancelled/unknown | 沿用；页面不得把 succeeded 以外状态显示为完成 |
| 智能体任务 | 缺失 | 新增理解中、待补充、待确认、执行中、待人工处理、完成、失败、取消 |

## 7. 产品动作与字段写回

| 产品动作 | 主要写入对象 | 账本要求 |
| --- | --- | --- |
| 上传或交接资料 | ingestion_batch、material、material_version | 记录原件、范围和提交目的 |
| 接受智能体归类 | candidate/object_relation + 专用关系表 | 保留建议和人工决定 |
| 确认建设依据 | source_clause、construction_item、scope_decision | 固定来源版本和影响范围 |
| 下达任务 | task、agent_confirmation | 区分任务草稿和正式派发 |
| 提交工作 | work_record_revision、task_submission | 绑定具体版本和材料 |
| 确认进度 | calculation_snapshot、progress_judgement | 固定规则、截止点和证据 |
| 创建补充任务 | gap_analysis、corrective_action、task | 先建议，后确认生成任务 |
| 生成/修改成果 | report_version、citation、agent_task | 固定输入和每轮差异 |
| 审核和导出 | review_record、report_export | 只针对确切批准版本 |

## 9. 修订顺序

1. 先确认 13、14、15 的对象、状态和智能体协议；
2. 在功能字段设计中新增建设依据、智能体任务、知识吸收和问题差距对象；
3. 调整工作记录、任务、进度、周期总结和引用结构；
4. 为 T01—T14 建立对象—动作—字段写回矩阵；
5. 设计技术数据模型时再确定具体表名、字段类型、索引和拆表方式；
6. 用 T01—T18 和 A01—A11 做反向完整性检查。

## 10. 当前不能写死的字段

- 学校真实组织层级和岗位名称；
- 试点专业群、专业、人员及权限；
- 指标的具体计算公式和去重键；
- 最终成果模板变量和章节结构；
- T15—T17 的专用业务字段；
- 部署位置、保存期限和跨群共享审批人。

这些内容进入配置或待确认对象，不用演示数据替代学校决定。
