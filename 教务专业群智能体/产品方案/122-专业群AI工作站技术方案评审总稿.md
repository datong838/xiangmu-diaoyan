## 1. 评审目标

本稿回答“专业群 AI 工作站在产品上怎样承载学校的专业群建设工作，在技术上怎样保证这些工作可持续办理、可核对、可修改、可追溯”。评审不以页面数量、接口数量或数据库脚本数量作为完成标准，而核对以下问题：

1. 教师、专业负责人、专业群负责人和教务审核人员能否围绕同一项建设工作持续提交、修改、退回、确认和形成成果；
2. 专业群智能体是否真正参与任务理解、资料查找、内容整理、计划执行和后续跟进，而不是停留在问答窗口；
3. 面向多个专业群和上百个专业时，资料、组织、指标、任务和权限是否仍能保持独立、准确和可管理；
4. 零散资料、建设依据、日常工作、指标进度和正式成果是否由一套事实、关系、证据和版本贯穿；
5. 学校对数据资产拥有完整权利，数据可放在校内服务器或学校租赁并控制的私域云环境，我方云服务只提供动作能力；
6. T01—T18 是否都有明确产品入口、技术承载、人工责任和验收方法；
7. 哪些能力属于首期、选配、待校方确认或后续评估，是否清楚区分。

## 3. 系统定位

专业群 AI 工作站是一套面向学校专业群建设全过程的持续工作平台。它管理的核心不是一批静态文件，而是围绕建设目标不断发生的工作：建立依据、安排任务、提交进展、补充资料、确认事实、判断差距、形成成果、审核归档，并在新资料和新要求出现后继续推进。

系统具有三个同时成立的特征：

1. **重写入**：大量业务行为是提交、填写、修改、确认、退回、补充、关联、审核和归档；查询与展示服务于这些办理动作。
2. **事实与关系驱动**：文件只是来源，系统需要知道文件说明了什么、对应哪个专业和指标、由谁确认、在哪个期间有效、支撑了哪份成果。
3. **智能体协同**：专业群智能体贯穿每项工作，负责理解请求、组织资料、提出计划、调用受控能力、生成草稿、检查缺项和持续跟进；关键决定仍由学校人员确认。

## 4. 总体技术结构

```text
学校使用层
  教师工作台｜专业负责人工作台｜专业群负责人工作台｜教务审核工作台｜信息支持工作台
        ↓
业务办理层
  建设依据｜目标指标｜计划任务｜日常工作｜资料证据｜进度问题｜成果报告｜组织协作｜试点验收
        ↓
专业群智能体协同层
  请求理解｜范围确认｜任务知识包｜办理计划｜受控动作｜结果确认｜连续跟进
        ↓
专业群知识层
  专业档案｜事实｜关系｜证据｜规则｜模板｜版本｜适用范围｜冲突与未知
        ↓
可信记录层
  稳定对象｜不可变版本｜关系记录｜人工决定｜状态变化｜建设账本｜归档快照
        ↓
学校数据环境
  业务数据库｜文件原件与版本｜知识索引｜操作记录｜备份恢复

我方云动作服务
  文档理解｜内容整理｜表格生成｜文本生成｜分析辅助｜格式转换
  仅接收经授权任务所需的最小上下文，不持有学校数据资源
```

### 4.1 学校侧是业务事实的唯一落点

学校侧保存组织、人员、专业群、专业、依据、指标、任务、工作、资料、证据、成果、版本、决定和操作历史。任何云端动作输出都先作为候选结果返回学校侧，由学校侧校验权限、输入版本、任务状态和人工确认条件后，才能形成新的业务版本。

### 4.2 智能体是协同执行层

智能体不拥有绕过权限和人工确认的特殊通道。她通过与普通页面相同的业务动作完成工作，每次动作说明对象、范围、使用资料、形成结果、待确认事项和后续步骤。

### 4.3 知识库是专业群建设知识层

知识库不复制一套脱离原件的材料。它以学校文件和业务对象为来源，管理这些资料表达的事实、关系、规则、版本和适用范围，为查询、办理和成果编制提供经过确认的上下文。

### 4.4 建设账本是过程可信层

系统对新增、修改、提交、退回、确认、撤回、审核和导出形成追加记录。更正通过新版本和替代关系完成，历史不被静默覆盖，因此能够回答“当时根据什么、由谁决定、改了什么、影响了哪里”。

## 6. 四个保障中心

### 6.1 模板与业务规则中心

管理学校确认的模板、栏目、填写说明、统计规则、分类规则和生效版本。规则变化不改写历史结果，而是形成新版本并提示受影响的计划、指标、智能体任务和成果。

### 6.2 权限、资料使用与审计中心

权限同时判断人员角色、数据范围、任务责任、对象状态、敏感级别和动作类型。查看、下载、修改、确认、审核、导出分别授权。信息支持人员负责账号和运行保障，不因技术职责获得业务正文和代办权限。

### 6.3 试点、验收与运行保障中心

管理试点范围、参与人员、资料准备、用例、问题、复测和验收结论。合成演示、内部验证和学校现场验收分别记录，不能相互替代。

### 6.4 智能服务、后台任务与集成中心

管理服务能力、任务排队、失败重试、结果对账和外部工具连接。长任务保留输入版本和状态；结果未知时先查询业务事实和操作记录，不重复写入。

## 8. 核心对象和关系

### 8.1 稳定对象与版本分离

专业群、指标、任务、材料、成果等具有稳定身份；名称、正文、负责人、目标值和状态说明等变化形成版本。业务引用必须指明使用的是哪个对象和哪个版本。

### 8.2 关系需要独立管理

“材料支撑指标”“工作完成任务”“专业参与事项”“条款形成要求”“事实进入报告”等关系具有来源、提出人或提出方式、确认状态、有效期和确认人。智能体建议建立的关系必须先标记为候选。

### 8.3 五类陈述分开

系统区分来源摘录、候选事实、已确认事实、规则和人工决定。未知、冲突和缺项保留原状，不能为了生成顺畅文字而自动补成事实。

### 8.4 版本、状态和决定分开

新版本说明内容变了；状态说明当前处于草稿、待确认、已确认、退回或归档；决定说明谁批准了什么。三者不能压缩成一个字段。

## 9. 专业群智能体运行主线

```text
接收自然语言任务
  → 识别学校、专业群、专业、期间、对象和期望结果
  → 显示任务范围与需要使用的资料
  → 从专业群知识库建立本次任务知识包
  → 形成可解释的办理计划
  → 对写入、发送、确认、正式导出等动作请求人工确认
  → 调用受控能力并保存回执
  → 将结果作为候选版本返回工作台
  → 人员核对、修改或确认
  → 写入新版本、关系、决定和建设账本
  → 继续跟踪缺项和下一步
```

当资料不足、权限不足、版本已变化、规则冲突或能力未开放时，智能体停止相应动作，说明原因和需要补充的条件。

## 10. 专业群知识库技术主线

```text
学校资料登记
  → 固定原件与版本
  → 按页、段、表、图片说明形成内容单元
  → 识别对象、事实、关系和规则候选
  → 人工核对
  → 发布为具有范围和版本的正式知识
  → 建立结构化、全文和关系索引
  → 按角色、专业群、专业、期间和任务目的检索
  → 返回来源位置、适用范围、确认状态和资料截止时间
```

知识库按学校、专业群、专业、建设周期和任务范围组织。跨专业共建通过明确关系汇总，不复制成互相矛盾的多份事实。跨群复用只复用结构、方法和空模板，不复制另一专业群的事实、材料、人员和结果。

## 11. 关键非功能要求

| 方面 | 方案要求 |
| --- | --- |
| 一致性 | 同一写操作中的新版本、关系、人工决定和账本记录要么共同成功，要么共同失败 |
| 并发 | 提交时校验使用的当前版本；发现他人已修改时返回差异，不自动覆盖 |
| 幂等 | 重复提交同一业务动作不能形成重复版本、重复任务或重复关系 |
| 可追溯 | 正式数字、文字和结论能回到对象、版本、来源位置和确认人 |
| 隔离 | 默认按学校和专业群隔离；跨群共享需要明确对象、用途、范围和期限 |
| 数据主权 | 学校拥有数据资产完整权利，并控制部署、备份、导出、撤权和处置 |
| 恢复 | 数据库、文件、索引、版本指针、关系和账本按同一恢复点核对 |
| 可用性 | 长任务可查看状态、暂停、恢复和失败原因；结果未知先对账 |
| 可扩展 | 新专业群通过配置和独立初始化建立；新任务通过对象与能力单元扩展 |

具体性能数值、容量、保留周期、可用性目标和恢复目标需结合学校环境和试点规模在评审中确认，当前不编造指标。

## 12. 集成与部署边界

### 12.1 学校数据环境

可部署在学校内部服务器，或学校租赁并控制的私域远程云服务器。部署位置不改变学校对数据库、文件、索引、版本、账本和备份的完整权利。

### 12.2 我方云动作服务

云端只提供经批准的文档理解、内容生成、格式处理等动作能力。每次调用由学校侧形成最小任务信封，限制任务目的、允许使用的内容、返回结构、有效时间和调用次数。云端不建立学校资料库，不把学校数据转成我方资产。

### 12.3 学校现有系统

本期先保留人员、组织、账号、文件和数据导入导出的适配边界。是否连接统一身份、教务系统、办公平台或文件平台，由学校确认现有系统和授权方式后单独评审，不在当前方案中默认承诺直连。

## 13. 评审时必须形成的决定

1. 九个业务工作区和四个保障中心是否构成完整产品范围；
2. T01—T14 的首期优先级，T15—T17 的选配边界及 T18 的推广条件；
3. 四类学校角色和信息支持角色的职责、查看范围和确认责任；
4. 建设依据、指标规则、进度结论、成果审核的最终确认人；
5. 专业群智能体允许执行的读操作、草稿操作和需要人工确认的写操作；
6. 专业群知识库允许进入正式范围的资料类型、确认流程和更新责任；
7. 学校数据部署位置、备份责任、云动作调用范围和禁止传输内容；
8. 试点专业群、专业、人员、建设周期、真实样例和首份成果模板；
9. 性能、容量、恢复、日志保留和验收口径；
10. 评审后哪些文档修订为冻结版本，哪些仍保留待确认。
