# 专业群 AI 工作站方案文档地图设计说明

> 版本：v0.1  
> 日期：2026-10-21  
> 状态：导航设计基线  
> 范围：只整理现有文档关系并生成本地导航，不修改方案正文，不进入产品编码

## 1. 建设目的

现有资料同时包含业务依据、产品方案、设计校核、视觉原型反馈、技术初稿、编码后形成的实现材料和当前评审稿。文件编号能够反映形成顺序，却不能独立回答以下问题：

1. 评审应先看什么、再看什么；
2. 哪些文档决定业务与产品，哪些文档只用于校核或参考；
3. 当前待评审方案与历史实现记录是什么关系；
4. 一份总方案由哪些分方案支撑，又由哪些追踪矩阵和验收方案检查；
5. 怎样从树形总览快速回到原始 Markdown 文档。

因此新增一个自包含的本地 HTML“方案文档地图”，把原文保留在原处，只在导航中维护阅读结构、文档状态、关系和入口。

## 2. 本轮 Rules

1. 先读项目现有导航、来源分层索引和完成审计，再设计树形关系；
2. 先完成本设计说明，再编写导航生成程序与页面模板；
3. 只新增 `产品方案/方案导航资料/` 下的维护文件及一份 HTML 入口，不改动现有正文；
4. 每份文档只能有一个主树位置，不能因多重用途在主树中重复出现；
5. 文档间的交叉依赖放入局部关系图，不能把编号先后误写成继承关系；
6. 明确区分业务依据、待评审设计、校核材料、原型反馈、技术初稿和历史实现材料；
7. “存在实现记录”不能显示为“方案已评审”或“产品已完成”；
8. 页面必须离线可用，原文链接使用相对路径，不依赖外网或产品服务；
9. 生成后检查覆盖数、稳定编号、链接、搜索、展开收拢、深链接和常用投影分辨率；
10. 后续刷新必须复用稳定编号，不因新增文档重新编号旧节点。

## 3. 主树结构

主树采用八个一级分支：

| 一级分支 | 主要内容 | 阅读作用 |
| --- | --- | --- |
| 业务依据与校方沟通 | 面谈材料、需求确认单、校方沟通稿、功能字段稿和探索材料 | 回答“学校提出了什么、哪些仍需确认” |
| 核心产品设计 | 00—18 | 回答“产品怎样承载业务” |
| 设计校核与追踪 | 19—26 | 检查对象、字段、流程和 T01—T18 是否一致 |
| 当前方案评审稿 | 122—138 | 本轮评审、学校准备和评审后工作的正式入口 |
| 视觉原型与页面验证 | 27—37 及 `demo` 内设计说明 | 检查页面能否承载方案，不反向扩大需求 |
| 首版技术初稿 | 38—44 | 为当前技术评审提供历史技术思路 |
| 历史实现与验证材料 | 45—121 | 说明曾经实现或验证过什么，不决定产品应怎样设计 |
| 项目辅助资料 | 项目资料索引、选型和早期探索资料 | 辅助追溯，不作为单独范围承诺 |

主树顺序表达阅读优先级，不表达文件创建时间、代码依赖或实施完成度。

## 4. 当前评审主线

导航首页提供以下评审捷径，但捷径不复制文档节点：

1. `138-方案文档完成审计与评审交付清单.md`：确认本轮交付边界；
2. `122-专业群AI工作站技术方案评审总稿.md`：阅读技术总方案；
3. `132-T01至T18需求产品技术验收追踪矩阵.md`：检查需求、产品、技术和验收是否贯通；
4. 123—126、129—130、135—137：按领域阅读分方案；
5. `127-技术方案评审清单与未决事项.md` 与 `133-产品与技术方案评审会议材料.md`：组织评审并记录结论；
6. `128-方案文档来源分层与评审使用索引.md`：发生来源争议时追溯；
7. `134-评审结论与现有实现差异分析模板.md`：评审形成结论后再使用。

## 5. 文档状态表达

页面使用“资料性质”和“评审状态”两组信息，避免将不同维度混为一谈：

| 分支 | 资料性质 | 页面状态文案 |
| --- | --- | --- |
| 业务依据与校方沟通 | 业务依据 | 原始信息、整理结果或待校方确认内容 |
| 核心产品设计 | 产品设计 | 已编制、待评审，未冻结 |
| 设计校核与追踪 | 校核材料 | 用于检查，不单独决定范围 |
| 当前方案评审稿 | 当前评审稿 | 已完成本轮编制、等待评审 |
| 视觉原型与页面验证 | 原型反馈 | 页面验证结果，不等于需求或验收通过 |
| 首版技术初稿 | 历史技术稿 | 供当前评审参考，未批准 |
| 历史实现与验证材料 | 实现参考 | 说明历史实现事实，不是评审基线 |
| 项目辅助资料 | 辅助资料 | 仅作选型、探索或资料管理参考 |

## 6. 关系类型

局部关系图只显示可解释的关系：

- `业务依据支撑`：业务原文、需求确认单或功能清单支撑产品设计；
- `产品方案分解`：产品总方案分解为专项产品方案；
- `详细设计落实`：详细设计落实某个产品能力；
- `校核`：一致性、字段差异或追踪矩阵检查被校核文档；
- `技术承载`：当前技术分方案承载产品方案；
- `验收追踪`：追踪矩阵、试点或验收方案检查产品与技术；
- `评审入口`：会议材料、清单或审计指向待评审方案；
- `历史参考`：旧技术稿或实现记录为当前评审提供可行性与差异参考；
- `正文引用`：原文存在明确 Markdown 链接。

关系必须能说明用途。没有依据的编号相邻关系不进入图谱。

## 7. 页面交互

1. 左侧按八个一级分支显示文档数量；
2. 主区以可展开、可收拢的横向树显示层级；
3. 支持标题、路径、章节和摘要搜索；
4. 点击文档打开详情栏，显示性质、状态、路径、章节、摘要、关联和原文入口；
5. 支持局部关系图，分别显示“哪些文档支撑它”和“它继续支撑哪些文档”；
6. 支持 `#doc=<稳定编号>` 深链接；
7. 支持缩放、复位、深浅主题和窄屏侧栏；
8. 首页明确显示“方案已编制、待评审、未冻结、未授权继续编码”。

## 8. 文件安排

```text
产品方案/
├── 专业群AI工作站方案文档地图.html
└── 方案导航资料/
    ├── 00-专业群AI工作站方案文档地图设计说明.md
    ├── README.md
    ├── 生成导航.py
    ├── 导航模板.html
    ├── 稳定节点ID.json
    ├── 文档图谱数据.json
    ├── 来源阅读与分类台账.jsonl
    ├── 导航核查记录.json
    └── 静态交互核查.mjs
```

生成数据与 HTML 是可重建产物；稳定节点 ID 文件必须长期保留。

## 9. 完成标准

1. 纳入目标目录中全部业务与方案 Markdown，排除依赖包、生成物和导航自身维护文件；
2. 每份文档主树归属唯一；
3. 所有关系端点均能找到文档；
4. 所有原文相对链接存在；
5. 搜索、展开、收拢、缩放、主题、详情和深链接可用；
6. 1440×900、1600×1000、1920×1080、2048×1320 下无关键内容遮挡；
7. 导航页面明确当前评审边界，不将历史实现材料提升为现行设计依据；
8. 输出生成时间、文档数量、关系数量、来源指纹和 HTML 指纹，便于后续判断是否过期。
