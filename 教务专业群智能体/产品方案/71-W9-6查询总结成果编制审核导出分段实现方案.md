# W9-6 查询、总结、成果编制、审核与导出分段实现方案

> 版本：v1.0　日期：2026-10-18　状态：编码前冻结稿。  
> 对应任务：T09、T12、T13、T14。  
> 前置：第 13—15、22、39、41—43、69—70 份方案与记录。  
> 本文职责：把即时查询、周期总结、正式成果、局部改稿、独立审核和文件输出实现为共享事实基线的一条产品链。

## 1. 总体目标

W9-6 不建设四套相互独立的文字生成功能。系统先固定一批有范围、有截止点、有版本、有确认状态的事实，再让查询、总结和正式成果分别使用这批事实：

```text
已确认任务、工作、进度、差距和知识
  → 统一事实快照
      ├─ T12 结构化查询结果
      ├─ T09 周/月/年总结与下期计划草稿
      └─ T13 成果编制任务
             → 章节与引用
             → T14 指定范围改稿
             → 独立审核
             → 正式导出与归档
```

事实快照回答“当时依据哪些对象和版本”；查询结果回答“怎样查看”；周期总结回答“这一期间做了什么、还差什么”；正式成果回答“按哪个模板形成哪一版交付件”。后面的文字不能反向改写前面的事实。

## 2. 分段

| 分段 | 建设内容 | 完成标志 |
| --- | --- | --- |
| W9-6A | 统一事实快照、结构化查询、查询快照、周期总结及下期计划草稿 | 同一快照可以形成带来源查询表和月度总结；数字、截止点、缺项一致；总结确认不自动派发任务 |
| W9-6B | 模板版本、成果编制任务、输入快照、章节、引用、缺项和支撑目录 | 年度报告或中期评审可固定模板与事实快照，逐章形成可编辑草稿并回到来源 |
| W9-6C | 指定范围改稿、人工保护块、版本差异、独立审核、草稿/正式导出和归档 | 局部修改不影响保护内容和锁定事实；作者不能自审；正式导出只来自批准版本 |

本轮先编码 W9-6A。6B、6C 只冻结依赖和边界，不提前返回模拟成功。

## 3. 统一事实快照

### 3.1 对象

- `reporting_snapshots`：稳定快照编号、学校、专业群、周期、专业范围、统计期间、数据截止点、建立人、当前状态和摘要；
- `reporting_snapshot_sources`：进入快照的来源对象、来源版本、来源种类、确认状态、用途和摘要；
- `reporting_snapshot_facts`：从来源确定性形成的事实行，保存事实种类、主体引用、结构化数值、显示状态、来源引用和事实摘要。

首批允许来源：

1. 已有正式进度确认的指标计算运行；
2. 当前可见的任务版本及其工作记录、提交版本数量；
3. 指标运行中形成的差距项。

知识条目、材料正文、周期计划和更多事实类型在后续扩展，但首批表结构不能阻止扩展。

### 3.2 约束

- 快照必须固定 `period_start`、`period_end` 和 `as_of`；
- 来源对象必须属于同一学校、专业群和建设周期；
- 指标计算没有负责人正式进度确认时不能作为正式事实进入快照；
- 任务事实固定当时 `task_version_id`，后续任务变化不改写旧快照；
- 来源、事实和快照建立后不可更新或删除；更换范围、截止点或来源时建立新快照；
- 快照只保存结构化事实与引用，不复制材料正文和文件内容。

### 3.3 首批事实种类

| 事实种类 | 固定内容 |
| --- | --- |
| `indicator_progress` | 指标规则版本、目标值、负责人确认实际值、差值、确认决定、截止点 |
| `indicator_gap` | 差距种类、状态、建议动作和来源输入引用 |
| `task_status` | 任务版本、专业、责任人、状态、截止日、工作记录数、提交版本数 |

## 4. W9-6A：结构化查询

### 4.1 查询对象

- `reporting_queries`：一次保存下来的查询，固定原始问题、结构化查询类型、结果栏目、使用的事实快照和建立人；
- `reporting_query_rows`：按确定性规则形成的表格行，每行保留事实编号和来源引用；
- 查询结果为追加式快照，不改变任务、指标或材料状态。

首批查询类型：

- `indicator_progress`：目标、已确认实际、差距和截止点；
- `task_follow_up`：按责任人和任务列出状态、节点、工作记录数和提交数；
- `group_overview`：组合指标进度、任务状态和差距，形成专业群建设概览。

用户原话保留在学校侧；首批由明确 `queryKind` 驱动确定性表格，不能据此宣称开放式语言理解已经完成。

### 4.2 输出要求

结果必须同时返回：

- 学校、专业群、周期和专业范围；
- 统计期间、数据截止点和快照编号；
- 表格栏目和结构化数据行；
- 每行事实引用和源对象版本；
- 未知、缺项和冲突；
- 数据更新时间和可以继续执行的产品动作。

## 5. W9-6A：周期总结与下期计划

### 5.1 对象

- `cycle_summaries`：稳定总结编号、类型、期间、快照、建立人和当前版本；
- `cycle_summary_versions`：草稿正文结构、确认状态、人工修改内容、变更原因和内容摘要；
- `cycle_summary_items`：本期完成、计划差异、未完成原因、遗留事项和下期计划建议，每项绑定事实引用；
- `cycle_summary_decisions`：负责人对确切总结版本作出 `confirm`、`return` 或 `reject`。

首批总结类型为 `weekly`、`monthly`、`annual`。手工建立和定时建立以后共用同一对象；本波只实现手工建立，不能模拟定时任务。

### 5.2 确定性草稿结构

```text
本期完成情况
  - 已确认完成的指标和任务
计划与实际差异
  - 指标差值、进行中和逾期待确认任务
未完成及原因
  - 按差距种类和任务状态列出
遗留事项
  - 仍需补工作、补材料或确认口径的事项
下期计划建议
  - 从未关闭差距和未完成任务形成建议，不自动建立或派发任务
```

每一项区分“已确认事实”和“建议”。建议不能进入正式指标，也不能因总结确认自动变成任务。

### 5.3 编辑和确认

- 建立总结先生成 v1 草稿；
- 用户编辑形成 v2、v3 等新版本，旧版本不覆盖；
- 编辑只允许补充说明和调整表达，锁定事实编号与数值不能在正文中静默改写；
- 负责人确认绑定确切版本；作者不得自己完成后续 W9-6C 的独立成果审核，但周期总结确认首批允许由专业群负责人确认本人发起的业务总结；
- `return` 后必须建立新版本再确认；
- 确认总结不自动创建、派发或完成任务。

## 6. W9-6B 依赖与边界

W9-6B 将新增：

- 模板、模板版本和栏目定义；
- 成果编制任务及输入快照；
- 成果章节、章节版本和人工保护块；
- 事实引用、引用定位、支撑材料目录和缺项；
- 年度报告与中期评审分别作为成果类型，不用一个模板替代另一类需求。

成果任务必须选择 W9-6A 的事实快照或建立新快照。缺正式模板时状态为“资料不足”，不能套用服务方自设模板形成正式稿。

## 7. W9-6C 依赖与边界

W9-6C 将新增：

- 修改要求、允许范围、基版本和人工保护块；
- 新版本、块级差异、引用变化和未执行意见；
- 审核提交、独立审核、退回、重审和批准；
- 草稿导出、正式导出、导出校验和归档。

正式导出必须同时满足：成果版本已批准、模板版本固定、事实引用有效、必填栏目完整、导出人有权。批准后任何修改都生成新草稿并重新审核。

## 8. W9-6A 接口

| 接口 | 行为 |
| --- | --- |
| `POST /reporting-snapshots` | 根据已确认指标运行和当前任务版本建立不可变事实快照 |
| `GET /reporting-snapshots/{snapshotId}` | 查看快照、来源、事实、范围和截止点 |
| `POST /reporting-queries` | 基于一个事实快照形成并保存结构化查询表格 |
| `GET /reporting-queries/{queryId}` | 查看查询栏目、行、事实引用和来源 |
| `POST /cycle-summaries` | 基于一个事实快照建立周期总结 v1 草稿 |
| `GET /cycle-summaries/{summaryId}` | 查看总结版本、条目、事实引用和决定 |
| `POST /cycle-summaries/{summaryId}/versions` | 从明确基版本形成编辑版本，不修改锁定事实 |
| `POST /cycle-summaries/{summaryId}/decisions` | 负责人确认、退回或拒绝确切版本 |

写接口继续使用统一操作信封、期望版本、幂等键、回执、建设账本和 Outbox。

## 9. 权限

- 专业群负责人：可建立群级事实快照、查询和周期总结，可确认周期总结；
- 教务审核人员：可在授权群内读取快照、查询和已提交/已确认总结，不建立群级事实；
- 教师：首批不建立群级快照；本人任务查询继续使用 W9-5 已验证接口，专业级总结留到范围规则补齐后开放；
- 信息支持人员：只看运行健康，不看快照数量、问题原话、事实行或总结；
- 所有对象继续按任务发起人与服务端角色校验，不接受客户端自报角色。

## 10. W9-6A 失败和停止规则

- 没有正式进度确认的指标运行拒绝进入事实快照；
- 来源跨学校、跨专业群或跨周期时按不存在处理；
- 期间不合法、截止点早于期间开始、来源为空时拒绝建立；
- 查询类型与事实快照不匹配时保留明确缺项，不编造结果；
- 总结期间必须与快照期间一致，不能重新解释截止点；
- 旧总结版本编辑或决定返回版本冲突；
- 已确认版本不能直接改写，只能建立后续草稿版本；
- 同一幂等请求不重复建立快照、查询、总结版本或决定；
- 写入失败整事务回滚，结果未知先按操作编号对账。

## 12. W9-6A 自测门槛

1. 用目标 3、负责人确认实际 1、尚差 2 的指标运行和 B/D 任务建立 6 月事实快照；
2. 快照固定指标规则版本、正式进度确认、任务版本、截止点和事实摘要；
3. `group_overview` 查询返回结构化表格，显示 A/B/D/C 的业务含义通过来源事实表达，核心数字与正式进度一致；
4. 用同一快照建立 6 月月度总结，本期完成、未完成、遗留和 7 月计划建议均能回到事实编号；
5. A 已完成内容不作为新的 7 月新增任务建议，B/D 未完成事项分别保留不同原因；
6. 编辑总结形成新版本，旧版本、事实数值和引用不变；
7. 负责人退回后必须建立新版本再确认，确认不自动建立或派发任务；
8. 未确认指标、跨群对象、其他教师、审核人员写入和信息支持访问均被拒绝且不泄露数量；
9. 同一幂等请求返回原回执，旧版本并发编辑返回冲突；
10. 快照、事实、查询行和决定均可回查到账本，不复制材料正文；
11. 迁移可从空库顺序执行并重复执行；
12. OpenAPI、编译、类型检查、全工程测试和方案一致性检查通过。

只有 6A 门槛全部通过后才标记 `W9-6A-verified`。W9-6 总波仍保持未完成，直到 6B、6C 通过。
