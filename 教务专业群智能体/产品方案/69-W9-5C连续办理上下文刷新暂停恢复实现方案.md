# W9-5C 连续办理、上下文刷新与暂停恢复实现方案

> 版本：v1.0　日期：2026-10-18　状态：编码前冻结稿。  
> 前置：第 15、41、65、67、68 份方案与验证记录。  
> 本文职责：把“后续要求仍属于原任务、资料变化后重新核对、暂停后可安全继续”落实为产品对象、状态、接口、数据边界和验证门槛。

## 1. 本波解决的问题

W9-5A、W9-5B 已经能够建立智能体任务、固定知识任务包、形成受控计划、逐步执行动作并在人工确认后建立任务草稿。本波补齐同一事项跨多轮持续办理的基础能力：

1. 用户补充条件或提出后续要求时，明确绑定原任务和当时的基版本；
2. 任务重新办理前，根据原范围、原意图和原目标重新收集当前事实；
3. 新旧上下文有无变化都形成检查结果，新一轮办理使用新任务版本、新知识包和新计划；
4. 用户可以暂停未结束任务，系统保留暂停原因、上次状态、未完成步骤和基线；
5. 恢复时重新检查权限、范围、事实版本、待确认事项和结果未知动作，不能沿用过期执行条件；
6. 旧任务版本、旧知识包、旧计划、旧动作和旧决定只读保留；
7. 学校正文、用户原话和业务对象快照仍保存在学校侧，不进入动作网关安全日志或外部服务持久层。

本波不接入外部生成模型，也不声称已经具备开放式自然语言多轮理解。连续办理通过明确的后续要求类型、版本绑定和确定性重新收集来验证协议。

## 2. 产品规则

### 2.1 同一任务与新任务的边界

以下后续要求可以继续原任务：

- 补充原任务缺少的条件；
- 修正原任务中的范围内信息；
- 要求按当前资料重新检查；
- 暂停后要求继续办理。

更换专业群、建设周期、原任务意图、目标对象或预期产出，均不允许作为普通后续要求静默覆盖。接口返回“需要新建任务”，由用户明确建立新任务。

### 2.2 版本与上下文规则

- 每条后续要求记录 `based_on_task_version_id`，旧版本提交返回版本冲突；
- 每次上下文刷新都新增任务版本、知识包和计划，即使内容摘要没有变化，也不复用已经执行过的计划；
- 新知识包按当前权限重新收集，不能复制旧知识包后假定仍然可见；
- 旧知识包在新一轮开始后标记为 `superseded`；若事实摘要改变，同时在检查记录中标为 `changed`；
- 新计划凡含草稿或正式写动作，必须重新确认，旧计划批准不能继承；
- 已批准成果不因新资料自动变化，本波只记录变化与影响，不修改旧成果。

### 2.3 暂停与恢复规则

- 只允许暂停尚未完成、未取消、未拒绝的任务；
- 暂停生成新任务版本和生命周期记录，保留暂停前状态、任务版本、知识包和计划；
- 暂停期间禁止继续执行动作或确认结果；
- 恢复必须由任务发起人发起，并在同一事务中重新收集上下文、创建新版本知识包和计划；
- 存在 `unknown` 动作结果时不得恢复执行，必须先按原操作编号完成只读对账；
- 恢复后根据当前条件进入 `waiting_for_input`、`waiting_plan_confirmation` 或 `ready_to_execute`，不会直接恢复到动作执行中。

## 3. 数据对象

### 3.1 `agent_task_messages`

保存原任务中的后续要求，不把聊天记录当作自由覆盖命令。

| 字段 | 说明 |
| --- | --- |
| `task_id` | 原智能体任务 |
| `based_on_task_version_id` | 用户提交时看到的任务版本 |
| `message_no` | 任务内连续编号 |
| `message_type` | `supplement`、`correction`、`refresh_request`、`resume_request` |
| `content` | 学校侧保存的用户补充原话 |
| `content_digest` | 内容摘要，用于留痕和对账 |
| `author_person_id` | 提交人 |
| `created_at` | 提交时间 |

### 3.2 `agent_context_checks`

保存每次重新收集的比较结果。

| 字段 | 说明 |
| --- | --- |
| `previous_task_version_id` | 刷新前任务版本 |
| `new_task_version_id` | 刷新后任务版本 |
| `previous_pack_id` / `new_pack_id` | 新旧知识包 |
| `trigger_type` | 后续要求、人工刷新或恢复 |
| `comparison_status` | `unchanged`、`changed`、`blocked` |
| `previous_digest` / `current_digest` | 新旧上下文摘要 |
| `changed_refs` | 发生变化的对象引用和版本，不保存正文 |
| `missing_items` / `conflicts` | 当前缺项和冲突 |
| `checked_by` / `checked_at` | 检查人和时间 |

### 3.3 `agent_task_lifecycle_events`

保存暂停、恢复和刷新事件。

| 字段 | 说明 |
| --- | --- |
| `event_type` | `paused`、`context_refreshed`、`resumed` |
| `from_status` / `to_status` | 状态变化 |
| `reason` | 用户给出的原因 |
| `task_version_id` | 事件形成的新版本 |
| `baseline` | 暂停前版本、知识包、计划和未完成步骤编号 |
| `actor_person_id` / `created_at` | 操作人和时间 |

三类记录均只能追加，不能更新或删除。

## 4. 状态与操作

新增任务状态 `paused`。继续办理不新增“会话状态”，而是通过任务版本、消息、上下文检查和生命周期事件表达。

```text
原办理状态
  ├─ 暂停 → paused
  │           └─ 恢复并重新检查
  └─ 补充 / 修正 / 刷新请求 → 重新检查
                                ├─ 缺条件 → waiting_for_input
                                ├─ 含写计划 → waiting_plan_confirmation
                                └─ 纯查询 → ready_to_execute
```

`completed` 任务允许由 `refresh_request` 开启新一轮办理，但仍创建新版本、知识包和计划；已完成动作和结果不重写。

## 5. 接口

| 接口 | 行为 |
| --- | --- |
| `POST /agent-tasks/{taskId}/messages` | 记录后续要求并立即创建新一轮上下文、知识包和计划；要求当前任务版本 |
| `POST /agent-tasks/{taskId}/refresh-context` | 不新增用户消息，按原任务意图重新收集并创建新一轮；要求当前任务版本 |
| `POST /agent-tasks/{taskId}/pause` | 保存暂停原因、原状态和未完成步骤；要求当前任务版本 |
| `POST /agent-tasks/{taskId}/resume` | 保存恢复要求，重新核权和收集上下文，再创建新一轮；要求当前暂停版本 |
| `GET /agent-tasks/{taskId}` | 增加消息、上下文检查和生命周期事件，不改变既有字段 |

所有写接口继续使用统一写入信封、幂等键、期望版本、建设账本、Outbox 和回执。

## 6. 重新收集算法

1. 锁定任务并校验学校、专业群、周期、发起人和期望版本；
2. 拒绝切换范围、意图、目标对象或预期产出；
3. 检查是否存在结果未知动作；存在时记录 `blocked`，不创建可执行计划；
4. 使用原任务结构化意图调用现有 `gather`，按当前身份和权限重新读取对象；
5. 计算新知识包摘要，并与当前知识包摘要比较；
6. 创建新任务版本、新知识包、新计划和计划步骤；
7. 标记旧知识包为 `superseded`，追加上下文检查和生命周期事件；
8. 返回变化状态、缺项、冲突、新任务状态和是否需要重新确认计划。

变化引用通过旧、新知识包条目的 `object_type + object_id + object_version_id + item_digest` 比较形成。只返回引用和摘要，不在安全日志中包含对象标题、文件名、正文、用户原话或业务快照。

## 7. 动作网关最小上下文

本波只定义并验证可用于后续云能力的最小连续办理信封，不发送到任何外部地址：

```text
taskRef
taskVersionRef
knowledgePackDigest
planDigest
scopeProofDigest
changedObjectRefDigests[]
allowedActionCodes[]
stopPointCodes[]
```

信封禁止出现用户原话、后续消息正文、学校名称、人员姓名、材料标题、文件名、知识条目正文、对象快照和动作输入正文。动作网关仍保持 `externalEndpoints=[]`、`externalAiEnabled=false`。

## 8. 权限与失败处理

- 只有任务发起人且具备 `agent:execute` 权限时，才能补充、刷新、暂停和恢复；
- 无权或跨范围对象按不存在处理，不泄露任务是否存在；
- 重复幂等请求返回原回执，不重复创建消息、版本、知识包或计划；
- 旧版本、暂停状态下继续动作、非暂停任务恢复、已结束任务暂停均返回明确冲突；
- 重新收集失败时整个事务回滚，旧任务仍停留在原状态；
- 新上下文存在缺项或冲突时保留新一轮记录并停在 `waiting_for_input`；
- 不自动重试未知结果，不用新操作编号绕过原动作对账。

## 10. 自测与通过门槛

1. 在已完成的纯查询任务上提交 `refresh_request`，生成新任务版本、知识包和计划，旧记录保持不变；
2. 当前业务对象版本未变时，上下文检查为 `unchanged`，但新一轮计划仍独立可执行；
3. 当前任务或规则版本变化后，检查为 `changed`，变化引用可回查，新计划重新确认；
4. 旧任务版本提交后续要求返回版本冲突，不产生半条消息；
5. 暂停任务后动作执行被拒绝，详情显示暂停原因、原状态和未完成步骤；
6. 恢复时重新核权和收集上下文，生成新版本；权限已撤销或存在未知动作时不能恢复；
7. 含写动作的新计划不继承旧批准；纯查询计划进入 `ready_to_execute`；
8. 同一幂等请求不重复创建消息、知识包、计划和事件；
9. 信息支持人员、其他教师和跨群身份看不到任务内容、数量或消息；
10. 最小上下文信封和安全日志中不出现学校正文、消息正文、文件名、人员姓名或对象快照；
11. 外部地址为空、外部智能服务关闭；
12. 空库顺序迁移、重复迁移、编译、类型检查、全工程测试和 W9-4C—W9-5C 累积集成全部通过。

只有上述门槛全部通过后，才把系统阶段从 `W9-5B-verified` 更新为 `W9-5C-verified`。
