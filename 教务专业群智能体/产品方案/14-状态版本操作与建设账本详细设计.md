# 专业群 AI 工作站状态、版本、操作与建设账本详细设计

> 版本：v1.0　日期：2026-10-18　状态：内部评审稿。  
> 对应波次：W1、W3、W4—W7。  
> 文档职责：定义对象怎样变化、版本怎样保留、动作怎样受控，以及系统怎样形成可追溯且不能被后续覆盖的建设账本。

## 1. 产品原则

专业群建设持续多年，同一任务、材料、规则和成果会多次变化。系统不能只保存“当前值”，必须同时回答：

- 当前采用什么；
- 以前是什么；
- 谁在什么时候为什么修改；
- 修改影响了哪些指标、任务和报告；
- 哪些内容仍待人工确认；
- 一次操作失败或结果未知时，是否真的写入成功。

因此产品采用“业务对象当前状态 + 不可覆盖版本 + 追加式操作记录 + 影响关系”的建设账本。

## 2. 四种彼此独立的状态

一个对象不能只用一个状态字段概括全部情况。

| 状态维度 | 回答的问题 | 示例 |
| --- | --- | --- |
| 业务状态 | 工作进行到哪一步 | 草稿、已提交、被退回、已完成 |
| 确认状态 | 内容是否经过有权人员确认 | 未确认、部分确认、已确认、已失效 |
| 版本状态 | 当前版本如何使用 | 编辑中、候选、当前有效、已替代、已封存 |
| 处理状态 | 系统动作执行到哪里 | 待处理、处理中、成功、失败、结果待核对、已取消 |

例如：一份协议材料可以是“业务上已提交、内容已确认、v2 当前有效、文字提取处理成功”。四者不能压缩为一个“已完成”。

## 3. 通用业务状态机

```text
草稿
  → 已提交
  → 待核对
  → 已确认
  → 已归档

已提交/待核对
  → 被退回
  → 修改中
  → 再次提交

任一未归档状态
  → 已取消

已确认/已归档
  → 因新版本或新决定标记为已失效
```

并非所有对象都走完整状态机，但任何简化必须保留提交、确认和历史边界。

## 4. 主要对象专用状态

### 4.1 依据文件与条款

| 对象 | 状态 |
| --- | --- |
| 依据文件版本 | 草稿、待批准、已批准、已失效、已封存 |
| 原文条款 | 待提取、待核对、已确认、有冲突、已失效 |
| 口径冲突 | 新发现、待处理、已作决定、重新打开 |
| 口径决定 | 草稿、待确认、已生效、已撤销、已替代 |

### 4.2 任务与工作记录

| 对象 | 状态 |
| --- | --- |
| 任务 | 草稿、待确认、待执行、进行中、待验收、已完成、被退回、已取消 |
| 工作记录 | 草稿、已提交、待核对、已确认、被退回、已作废 |
| 问题 | 待识别、待确认、处理中、待复核、已关闭、重新打开 |
| 补充任务 | 建议中、待确认、已下达、执行中、已完成、已取消 |

### 4.3 材料、事实与证据

| 对象 | 状态 |
| --- | --- |
| 材料版本 | 已接收、解析中、可读取、部分可读、无法读取、已替代、受限 |
| 候选事实 | 待核对、已接受、已修改接受、已拒绝、有冲突 |
| 证据关系 | 候选、待补充、已确认、被拒绝、已失效 |
| 成果 | 草稿、待确认、已确认、重复待处理、已失效 |

### 4.4 指标与成果编制

| 对象 | 状态 |
| --- | --- |
| 进度判断 | 计算中、建议已形成、待确认、已确认、待复核、已失效 |
| 编制任务 | 准备中、资料不足、编写中、待审核、被退回、已批准、已归档 |
| 草稿版本 | 编辑中、已提交、被退回、已批准、已替代、已封存 |
| 导出件 | 生成中、生成成功、生成失败、已作废 |

## 5. 版本模型

### 5.1 版本触发条件

以下变化必须生成新版本：

- 正文、数值、统计规则或适用范围变化；
- 文件被替换或补充；
- 计划节点、责任人或预期产出变化；
- 报告章节发生人工或智能体修改；
- 模板结构、栏目或格式要求变化；
- 已确认关系被修改；
- 人工决定发生替代或撤销。

仅查看、下载、评论或添加不改变正文的备注不生成对象内容版本，但必须形成操作记录。

### 5.2 版本结构

每个版本记录：版本编号、基版本、创建人、创建方式、创建时间、变更原因、变更摘要、正文或结构快照、适用范围、确认状态、引用情况和替代关系。

### 5.3 版本规则

1. 新版本只能从明确基版本产生。
2. 已被正式成果引用的版本不可物理覆盖。
3. 当前有效版本变化后，旧版本保留并标记“已替代”。
4. 并行编辑产生两个候选版本时，由人选择合并、保留或拒绝。
5. 恢复旧版本实际生成一个以旧内容为基础的新版本，不删除中间历史。
6. 智能体改稿与人工改稿使用同一版本机制，并标明生成方式。

## 6. 建设账本记录

每次关键动作追加一条账本记录，至少包括：

| 字段 | 内容 |
| --- | --- |
| 记录编号 | 全局唯一 |
| 操作者 | 用户、智能体或后台服务；智能体动作同时记录发起用户 |
| 动作 | 创建、修改、提交、确认、退回、审核、授权、撤权、导出等 |
| 业务对象 | 对象编号、类型和版本 |
| 动作前状态 | 操作前的业务、确认和版本状态 |
| 动作后状态 | 操作后的业务、确认和版本状态 |
| 变更内容 | 字段差异、关系差异或文件版本变化 |
| 动作依据 | 用户指令、审核意见、口径决定或自动规则 |
| 结果 | 成功、失败、结果待核对或已取消 |
| 时间与环境 | 时间、入口和必要的运行信息 |
| 影响对象 | 因本次变化需要复核的指标、任务或成果 |

账本用于追溯产品操作，不替代学校正式档案制度。

## 7. 写操作分级

| 级别 | 动作示例 | 产品要求 |
| --- | --- | --- |
| L0 只读 | 查看、检索、预览、对比 | 执行权限过滤；敏感查看形成记录 |
| L1 草稿 | 新建草稿、智能体生成、代填未提交表单 | 可撤销；不得进入正式统计 |
| L2 提交 | 提交工作、材料、任务或报告 | 明确提交对象、范围和版本 |
| L3 确认 | 确认事实、关系、任务、进度或口径 | 只有指定角色可做；记录决定依据 |
| L4 审核 | 退回、批准、重审 | 审核人与内容版本绑定 |
| L5 范围与权限 | 授权、撤权、跨群共享、资料清除 | 强校验并保留完整记录 |
| L6 正式输出 | 发布、归档、生成正式导出件 | 只能基于批准版本；可核对输出完整性 |

## 8. 人工确认设计

确认界面必须同时显示：

1. 本次要确认的具体内容；
2. 来源及所用版本；
3. 与现有事实或规则的差异；
4. 确认后将影响的任务、指标、报告和人员；
5. 可选动作：接受、修改后接受、拒绝、退回补充、暂不决定；
6. 确认人的角色和确认说明。

“批量确认”只能用于同一范围、同一动作和相同风险等级的项目，仍为每条对象保留结果。

## 9. 失败、重复和结果未知

- **失败**：明确未写入，允许修正后重试；
- **重复请求**：使用动作请求编号识别，不重复创建对象或版本；
- **结果待核对**：系统无法确定是否写入，先读取账本和对象当前状态，不得直接重发；
- **部分成功**：逐项显示成功和失败，不把整批标记为成功；
- **取消**：只取消尚未生效的处理；已产生的版本和账本记录保留；
- **后台处理中**：页面显示实际处理状态，不能提前显示“已完成”。

## 10. 变化影响处理

当依据、统计规则、任务、事实、证据或模板的当前有效版本变化时：

1. 写入新版本和替代关系；
2. 查找直接引用旧版本的对象；
3. 形成“待复核影响清单”；
4. 智能体说明可能影响，不自动改写正式结论；
5. 负责人逐项确认继续沿用、重新计算、重新编写或不受影响；
6. 完成后关闭影响项，并保留处理过程。

## 11. 页面必须呈现的记录

- 对象详情：当前状态、当前版本、来源、责任人和最近动作；
- 版本页：时间轴、版本差异、确认状态和引用对象；
- 关系页：候选、已确认、冲突和失效关系；
- 审核页：被审核版本、意见、退回修改和重审结果；
- 智能体任务页：理解、计划、所用资料、建议、待确认动作和写回结果；
- 建设账本：按对象、人员、动作、时间和结果查询；
- 影响清单：变化来源、受影响对象、处理人和处理状态。

## 12. 验收规则

1. 任何已确认对象都能查看确认前后内容和确认人。
2. 对已引用材料上传新版本，不改变旧报告引用的内容。
3. 被退回草稿修改后形成新版本，原审核意见仍可查看。
4. 智能体执行写操作时可区分草稿、提交和正式确认。
5. 相同请求重复到达不产生重复任务或成果。
6. 结果未知时能够通过读取对象与账本完成对账。
7. 依据或规则变化能够列出受影响的指标和报告。
8. 撤权后用户不能继续查看正文，但历史授权和操作仍可审计。
