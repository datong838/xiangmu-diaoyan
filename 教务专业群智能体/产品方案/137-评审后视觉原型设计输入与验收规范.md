# 评审后视觉原型设计输入与验收规范

> 版本：v0.1 评审准备稿  
> 日期：2026-10-19  
> 状态：等待产品与技术方案评审；当前不修改视觉原型代码  
> 目的：防止视觉稿只描述业务或只展示只读看板，要求原型真实呈现产品怎样承载写入、协同、智能体和事实关系

## 1. 视觉原型回答的问题

业务沟通稿回答“为什么建设、要做什么”。产品视觉原型必须进一步回答：

- 教师从哪里登记工作和资料；
- 负责人怎样派发、退回、确认和处理差距；
- 教务审核人员怎样核对依据、引用和成果版本；
- 专业群智能体怎样参与每一步；
- 文件、事实、关系、证据和版本怎样同时呈现；
- 多个专业群和专业怎样切换且不串用；
- 失败、冲突、缺项和等待确认时用户怎样继续办理。

## 2. 总体视觉原则

1. **重写入优先**：主要页面有明确的填写、提交、修改、关联、退回、确认或审核动作；
2. **对象优先**：页面围绕任务、工作、材料、指标和成果，不围绕静态栏目堆文字；
3. **智能体在场**：智能体显示当前理解、资料范围、办理计划、执行状态、待确认和下一步；
4. **关系可见**：能从当前对象看到它来源于什么、支撑什么、被什么引用；
5. **版本可见**：当前版本、历史版本、修改人、差异和审核状态清楚；
6. **角色真实**：教师、负责人、审核人员和信息支持人员看到的入口和动作不同；
7. **状态可办理**：缺项、退回、冲突和失败提供明确后续动作；
8. **投影可讲解**：信息层次清楚，但不能为了大屏简化掉业务操作和状态。

## 4. 全局页面骨架

### 顶部

当前学校、专业群、专业、建设周期、当前角色、搜索和专业群助手入口。

### 左侧

产品模块和角色待办，不以黑色重装饰压过业务区域；整体颜色与主工作区协调。

### 中部

当前对象的主要办理区。编辑表单、材料、关系、版本和操作按工作步骤组织。

### 右侧

专业群助手、依据与关系、待确认或影响提示。右侧不是只读聊天记录，而是能把建议带入中部办理区。

### 底部或固定区域

保存草稿、提交、退回、确认、审核等主动作，以及本次动作影响和版本说明。

## 5. 必须形成的关键页面链

### 5.1 快速收件与归类

上传/粘贴资料 → 登记来源和业务日期 → 智能体分类建议 → 待补项 → 负责人确认归类 → 查看材料用途与版本。

### 5.2 教师工作提交

选择任务或直接登记 → 填写工作 → 添加材料 → 智能体协助整理 → 提交固定版本 → 查看负责人反馈 → 补充新版本。

### 5.3 建设依据整理

登记三类文件 → 选择版本与批准状态 → 查看条款候选 → 三文件对照 → 冲突处理 → 正式发布要求。

### 5.4 指标与差距

查看目标和规则 → 查看构成事实与材料 → 系统计算 → 负责人确认 → 查看差距 → 建立补充任务。

### 5.5 成果编制和审核

选择模板 → 固定事实快照 → 章节编写 → 引用核对 → 局部改稿 → 提交审核 → 退回/批准 → 正式导出和归档。

### 5.6 专业群智能体任务

提出请求 → 范围预览 → 知识包摘要 → 办理计划 → 人工确认 → 动作进度 → 候选结果 → 修改/接受 → 写回和继续跟进。

## 6. 首页应体现的产品能力

首页不是统计大屏，也不是业务介绍页。建议同时呈现：

- 当前建设周期、专业群和角色；
- 我的待办、退回待补、等待确认和接近节点；
- 最近工作和资料入口；
- 目标指标的已确认进度、资料不足和差距；
- 正在编制或等待审核的成果；
- 专业群助手当前能协助的事项和正在办理的任务；
- 版本变化、依据冲突、权限或运行异常；
- 快速操作：记工作、交资料、建任务、查进度、编成果。

## 7. 事实与关系怎样呈现

对象详情提供关系区：

- 来源：来自哪份依据、任务或工作；
- 参与：哪些专业和人员；
- 支撑：支撑哪些指标或事实；
- 使用：被哪些总结、报告和申报材料引用；
- 变化：当前版本替代了什么，哪些对象受影响；
- 决定：谁确认、拒绝、撤回或审核。

关系可以采用列表、时间线或局部关系图。图形用于帮助理解，必须能进入具体对象和办理动作。

## 8. 专业群助手的视觉形态

助手需要有统一名称、形象和状态，但重点是工作能力：

- 显示“我理解的任务”；
- 显示将使用的专业群、期间、资料和规则；
- 显示办理步骤和需要确认的动作；
- 展示来源、缺项、冲突和停止原因；
- 提供“带入编辑区”“建立草稿”“形成任务建议”等受控动作；
- 任务中断后显示等待什么、由谁处理、怎样继续。

不能只显示聊天气泡，也不能让用户误以为智能体已经替代正式确认。

## 9. 多角色页面检查

| 页面能力 | 教师 | 专业负责人 | 专业群负责人 | 审核人员 | 信息支持 |
| --- | --- | --- | --- | --- | --- |
| 登记本人工作 | 可 | 可 | 可 | 通常只读 | 不可代办 |
| 提交材料 | 可 | 可 | 可 | 按范围 | 技术状态可见 |
| 退回工作 | 不可 | 本专业 | 全群范围 | 按审核职责 | 不可 |
| 确认指标 | 不可 | 按授权 | 按授权 | 核对/审核 | 不可 |
| 编制成果 | 协作 | 可 | 可 | 核对 | 不可 |
| 审核成果 | 不可审核本人 | 按职责 | 按职责 | 可 | 不可 |
| 管理账号运行 | 不可 | 不可 | 不可 | 不可 | 可 |

实际角色和动作在评审后调整，视觉原型不得用前端按钮隐藏代替服务端权限。

## 10. 状态与异常页面

每条关键流程至少设计：

- 空状态：没有资料、任务或模板；
- 待补状态：缺哪些信息和谁补；
- 退回状态：意见、范围和下一步；
- 版本冲突：谁修改、差异和重新处理；
- 权限不足：不泄露对象内容，说明申请或转交方式；
- 智能服务不可用：保留人工办理；
- 处理失败：原件或草稿是否保留、怎样重试；
- 结果待核对：禁止重复提交，提供对账入口；
- 能力未开放：说明范围状态和需要确认的条件。

## 11. 与业务沟通展示站的关系

业务沟通展示站继续用于说明为什么建设、谁使用、工作怎样运转和学校最终得到什么。产品视觉原型不重复其叙事页面，而把已确认业务转换为可操作系统。两者可相互链接，但角色不同。

## 12. 原型验收清单

- [ ] 九个业务工作区都有真实办理入口；
- [ ] T01—T18 能定位到页面链或明确的选配关闭页面；
- [ ] 教师至少能完成快速收件和工作提交；
- [ ] 负责人能派发、退回、确认和处理差距；
- [ ] 审核人员能核对来源、版本并审核成果；
- [ ] 专业群助手至少贯穿收件、工作、查询和成果四类任务；
- [ ] 事实、关系、证据和版本能相互跳转；
- [ ] 多专业群切换和跨群不可见有页面表现；
- [ ] 空、缺项、冲突、越权、失败和结果未知均有状态设计；
- [ ] 主要页面能在常用电脑分辨率下完成操作；
- [ ] 投影模式不隐藏关键关系和动作；
- [ ] 页面文案使用产品语言，不使用“我们怎么讲”的内部口吻；
- [ ] 原型新增能力都能回到已评审方案。

## 14. 当前结论

本规范只准备视觉设计输入，没有修改任何视觉原型。评审完成前，现有原型用于理解问题，不作为冻结产品界面；评审后应依据本规范和冻结方案重新核对与调整。
