## 1. 开发原则

1. 每一波先冻结方案和契约，再编码、测试和浏览器验证。
2. 先建立对象、版本、关系、权限、幂等和账本，再接入智能体。
3. 每波必须包含允许、拒绝、失败和恢复用例。
4. 页面完成、代码完成、自动测试通过和真实链验证分别记录。
5. 未完成能力关闭，不用演示数据返回伪成功。
6. 现有 `demo` 作为视觉参照，正式工程不复制其中的业务本地状态。

## 4. 首个可运行切片：SLC-01

### 4.1 业务范围

只实现一条最小但真实的数据链：

```text
建立学校、DEMO-G01、五个专业和 2026 周期
  → 登记建设任务书 v1
  → 建立条款“2026 年新增合作企业 3 家”
  → 建立指标、规则 v2 和证据要求
  → 建立 B 企业任务 v2
  → 教师提交材料 v1
  → 负责人退回并说明缺项
  → 教师提交 v2
  → 负责人确认任务办结
  → 指标运行仍返回 1/3，等待材料与进度确认
```

### 4.2 必须真实实现

- PostgreSQL 持久化；
- 对象稳定编号和版本；
- 教师与负责人两种角色；
- 任务状态转换；
- 文件元数据和合成文件校验值；
- 幂等键和版本冲突；
- 建设账本；
- 指标计算快照；
- API 和最小正式页面；
- 自动测试及浏览器链路。

### 4.3 明确暂不进入 SLC-01

- 真实学校身份提供方；
- 云端智能体和模型调用；
- 文档解析、全文和向量检索；
- 正式报告、Word/Excel/PPT 导出；
- T15/T16；
- 正式学校资料和外部发布。

这些能力在界面中保持关闭，不返回模拟成功。

### 4.4 验收用例

1. 教师只能看到本人 B 企业任务，不能确认指标。
2. 负责人可退回并确认任务办结，不能改写教师原提交。
3. v1、退回意见和 v2 都可回查。
4. 旧 `expectedVersionId` 更新返回冲突。
5. 同一幂等键重复提交只产生一个新版本和一条业务结果。
6. 模拟响应丢失后，按操作编号可只读查到原回执，不重复写入。
7. 任务完成后指标仍为 1/3，必须单独确认材料和进度。
8. 每次写操作能对应到账本中的前后版本和操作者。
9. 备份恢复后对象、版本和账本一致。
10. 页面刷新后状态来自数据库，不来自浏览器本地状态。
