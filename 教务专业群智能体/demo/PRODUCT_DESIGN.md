# 专业群 AI 工作站产品设计稿

> 本稿用于指导内部视觉原型。业务事实来自专业群需求确认单、功能与字段设计及校方沟通稿；“事实与关系”“建设过程账本”借鉴 Semantica 的产品思想，不表示本项目已经采用其技术或代码。

## 1. 产品定位

专业群 AI 工作站首先是一套多人持续写入、整理、修改、审核和形成成果的建设管理平台，其次才是进度看板和关系展示工具。这里的“写”不是只填写工作进展，而是管理专业群建设全过程中的各种建设对象。

它需要把学校原来分散在聊天、文件夹、表格、Word、会议记录和个人记忆中的工作，转成可以持续办理的建设记录：

- 教务和专业群负责人写目标、指标、任务、分工、审核意见和确认结论。
- 教师写工作进展、业务发生时间、参与人员、实际结果和可提供的资料。
- 报告编写人与审核人员写草稿、修改意见、修订稿和定稿结论。
- 专业群助手帮助整理、关联、检查缺项、对照事实和起草内容。
- 每次写入都进入建设过程账本，并与目标、任务、人员、资料和成果建立关系。

产品不能让用户先理解复杂的数据结构再工作。用户从“我要提交什么、修改什么、审核什么、请助手办什么”进入，系统在写入过程中帮助建立结构和关系。

### 1.1 “重写”覆盖的完整管理范围

业务沟通稿中的各项管理工作，在产品中都应有可创建、可修改、可审核、可确认、可查版本的承载位置：

| 管理对象 | 需要持续写入和管理的内容 |
| --- | --- |
| 散乱资料 | 聊天摘录、图片、表格、原始文件、会议记录和临时说明；整理后保留来源与原件 |
| 建设依据 | 申报书、建设任务书、实施方案的文件、批准状态、适用周期、版本及原文位置 |
| 目标与指标 | 建设目标、考核指标、目标值、判断条件、统计期间、阶段结果和差距 |
| 任务与分工 | 年度任务、临时事项、负责人、配合人、时间节点、预期成果和后续动作 |
| 日常工作 | 教师和教务实际做过的工作、参与人员、业务日期、结果、材料和修改说明 |
| 资料与证据 | 原件、正式或过程性质、版本、有效期间、能够证明什么以及不能证明什么 |
| 检查与审核 | 检查记录、审核意见、退回原因、冲突处理、确认人和正式结论 |
| 总结与成果 | 周月总结、年度计划、建设报告、中期评审、申报材料、证据目录和学校模板 |
| 组织与保障 | 学校、学院、专业群、专业、教师、教务和信息处的职责、查看范围与人员变化 |
| 试点与验收 | 演示资料、试点范围、问题记录、修复结果、验收事项和后续推广安排 |

这些对象不是十套割裂的表格。申报书中的一项要求可以形成指标，指标可以分解成任务，任务由教师的日常工作推进，工作形成资料，资料支持检查结论，结论进入报告并产生下一步任务。产品用关系把各类编辑界面连成一个完整的建设过程。

## 2. 三层产品结构

### 2.1 第一层：写作与办理

这是产品的主体，占据页面最大空间。

| 工作场景 | 主要使用人 | 写入内容 | 提交后的去向 |
| --- | --- | --- | --- |
| 建设目标和指标维护 | 教务、专业群负责人 | 目标值、年度、责任专业、判断标准、依据位置 | 形成指标版本，等待生效确认 |
| 任务分解与指派 | 专业群负责人、专业负责人 | 任务、责任人、时间、预期成果、所需资料 | 进入教师或负责人的待办 |
| 日常工作填报 | 教师、专业负责人 | 做了什么、何时、谁参与、结果、资料 | 助手整理关系，负责人确认 |
| 资料与证据维护 | 教师、资料管理员 | 原件、来源、日期、版本、修改说明 | 进入审核，确认后作为正式证据 |
| 指标结果确认 | 负责人、教务审核人员 | 实际值、完成结论、差距、采用证据 | 写入确认记录，进入报告统计 |
| 总结和报告编制 | 报告编写人、审核人 | 章节内容、引用、修改意见、修订说明 | 保存草稿版本，审核后定稿 |
| 新事项登记 | 教务、专业群负责人 | 新申报、新检查、新模板、临时任务 | 形成可补充任务，不丢失事项 |

### 2.2 第二层：事实与关系

关系展示服务于写入，不单独追求“图看起来复杂”。当用户写一条工作、上传一份资料或修改一个结论时，页面同时显示它与周围对象的关系：

`建设目标 → 分解任务 → 责任人员 → 工作事件 → 资料版本 → 指标结论 → 报告段落 → 后续任务`

每条关系应说明关系类型和确认状态，例如：

- T07 `来源于` 任务书 3.2 节。
- 李老师 `负责` B 企业签约任务。
- 6 月 14 日工作记录 `形成` 协议草稿 v1。
- 协议草稿 v1 `关联` 新增合作企业指标，但 `尚不能证明` 正式签约。
- “暂不计入”结论 `依据` 协议草稿 v1 和负责人核对记录。
- “补正式协议”任务 `由该结论产生`。

关系既帮助用户理解，也在写入时发挥校验作用：没有责任人、没有业务日期、没有关联目标或把历史资料误关联为本年成果时，系统应提醒而不是悄悄接受。

### 2.3 第三层：建设过程账本

账本记录写入和修改的全过程：

- 谁在什么时间创建了什么。
- 专业群助手做了哪些整理和建议。
- 谁修改了哪些字段，旧值和新值分别是什么。
- 哪个资料版本替代了哪个版本。
- 谁退回、为什么退回、补充后怎样再次提交。
- 谁确认了事实、关系、指标结论和报告版本。
- 哪条记录被作废，为什么作废；原记录仍能追溯。

账本不是普通操作日志。普通日志只说明“点过某个按钮”，建设账本要说明这次动作改变了哪个业务事实、产生了哪个版本、影响哪些任务和成果。

## 3. 角色工作方式

### 3.1 教师

教师首页重点是“待我填写”和“被退回需要修改”：

- 提交本人任务进展。
- 上传或补充过程资料、正式成果。
- 修改被退回的工作记录，形成修订版。
- 确认助手整理出的标题、标签和关联建议。
- 查看本人提交怎样支撑任务和指标。

### 3.2 专业群负责人

负责人首页重点是“需要我组织和确认”：

- 建立目标和任务之间的关系。
- 分解任务并指派到专业和教师。
- 核对教师提交的事实、材料和关联。
- 确认指标阶段结果，或退回补充。
- 把差距转成下一步任务。
- 组织总结、报告和申报材料。

### 3.3 教务与审核人员

教务首页重点是“需要我审核和统一口径”：

- 核对建设依据和指标口径。
- 审核指标结果、报告草稿和证据目录。
- 对冲突资料或不同版本作出人工处理。
- 退回并写明修改要求。
- 确认正式版本，但作者不能审核自己的报告。

### 3.4 专业群助手

专业群助手是数字员工，不是悬浮问答入口。她接受工作任务，并展示办理过程：

1. 理解使用者要得到什么结果。
2. 找到当前权限内的目标、任务、资料和历史版本。
3. 整理事实与关系，识别缺项和冲突。
4. 起草记录、任务、表格、报告或修改建议。
5. 把结果放入当前编辑区，标明使用依据和仍需确认的内容。
6. 由学校人员编辑、确认或退回。

## 4. 总览工作台的主次关系

总览按照“重写、轻看板”的顺序组织：

### 4.1 主区：当前工作编辑台

中央主区默认打开当前待办的写入界面，而不是一组只读指标卡。工作台上方先提供“管理对象总台”，让用户可以进入散乱资料、建设依据、目标指标、任务分工、日常工作、资料证据、审核结论、总结成果、组织保障和试点验收。当前事项内再提供四个高频编辑入口：

- `写进展`：填写工作事实并提交资料。
- `改资料`：基于原版本形成新版本和修改说明。
- `建任务`：把目标或问题写成责任明确的任务。
- `编成果`：在已确认事实基础上编写总结或报告。

编辑台始终显示当前上下文：当前专业群、建设周期、关联目标、任务、责任人、统计期间和资料版本。

### 4.2 左区：按身份变化的待办

待办不是只读列表。每项提供直接动作，例如“填写进展”“补正式版”“处理退回”“确认关系”“审核草稿”。切换教师、专业群负责人、教务身份后，待办和主按钮同步变化。

### 4.3 右区：专业群助手

助手区与当前编辑台共享上下文。用户可以要求：

- “把我这条工作整理完整。”
- “检查还缺哪些信息和资料。”
- “把这份协议关联到正确任务和指标。”
- “根据退回意见形成修订稿，但不要改变已确认事实。”
- “用这些已确认记录写年度报告第三部分。”

助手的建议可以一键填入编辑台，但填入后仍是草稿；提交、审核和确认由相应学校人员完成。

### 4.4 辅助区：关系和账本

- “关联上下文”紧邻编辑台，展示当前内容与目标、任务、人员、事件、资料和结论的关系。
- “建设过程账本”位于编辑台下方，展示写入、修改、退回、确认和作废记录。
- 关系图帮助当前写作，账本解释当前内容怎样形成，两者不抢占主编辑区。

## 5. 关键交互闭环

### 5.1 教师提交一条进展

1. 教师在待办中打开“推进 B 企业签约”。
2. 填写工作日期、参与人、实际进展和当前结果，上传协议草稿。
3. 助手建议关联 T07、T10 和“新增合作企业 3 家”，并提示草稿不能证明正式签约。
4. 教师确认关系后提交。
5. 系统新增“工作记录 v1”和“协议草稿 v1”，写入账本，状态为待负责人确认。

### 5.2 被退回后修改

1. 负责人退回并写明“补充正式签订日期和正式协议”。
2. 教师打开原记录，看到原内容、退回意见和受影响关系。
3. 教师上传正式协议并填写修改说明，形成资料 v2 和工作记录修订版。
4. 原 v1 保留，并显示“已被 v2 替代”；不能静默覆盖。
5. 再次提交审核，账本记录完整往返过程。

### 5.3 负责人确认指标结论

1. 负责人查看 A—D 企业的事实与证据关系。
2. 助手按年度、正式材料和有效活动三项条件形成建议。
3. 负责人确认 A 计入，B、D 暂不计入，C 不计入本年。
4. 系统写入阶段结论“已确认 1 家、尚差 2 家”。
5. 差距继续写成 B、D 两项后续任务；同一结论进入报告草稿。

## 6. 视觉原型本轮范围

本轮视觉稿先把总览重做为可操作产品工作台，重点验证：

- 浅色一体化导航。
- 教师、专业群负责人、教务三种身份切换。
- 中央写进展表单和 `提交并写入账本` 操作。
- 更新资料形成新版本的界面。
- 当前编辑内容的目标、任务、人员、资料和结论关系。
- 专业群助手接任务、给出缺项和把建议填入编辑台。
- 建设过程账本新增记录、修订关系和人工确认状态。

其余七个页面保留现有内容，后续再按同一产品模型逐页深化。本轮不能把“总览已可交互”误写为完整产品已经实现。

## 7. 产品界面文案原则

本原型是专业群建设管理系统，不是校方沟通稿的页面化复述。界面文案应直接说明系统模块、管理对象、用户动作和当前状态，避免沿用汇报、讲解或宣传语气。

- 页面主标题使用稳定的功能名称，例如“建设工作持续推进”“建设依据管理”“资料与证据管理”。
- 页面说明交代系统承载范围，例如“统一管理建设目标、任务、过程资料、审核记录与成果版本”。
- 表单字段使用可直接填写的对象名称，例如“工作内容”“工作结果”“修改说明”。
- 按钮使用明确操作，例如“应用建议到编辑区”“提交并写入账本”。
- 状态文字说明系统当前状态，例如“待复核”“已退回”“草稿自动保存”。
- 保留专业群助手的自然交流方式，但助手以外的页面标题、模块标题和系统提示不使用“先……”“把……”“都在这里……”“只需……”等讲解式表达。
- 业务事实、案例数据和学校易懂的用词继续保留；本轮只调整表达方式，不改变功能范围和业务口径。
