下面按“产品边界 → 技术架构 → 飞书底层能力（API/事件/SDK/CLI） → 豆包/火山侧能力 → 几种可落地集成模式 → 权限安全与运维”做一遍深度梳理。所有结论尽量区分「官方原生能力」和「自建开发方案」，避免把宣传话术当接口事实。

一、先理清产品边界：豆包、飞书、火山分别干什么

2026 飞书 8.0 + 豆包工作整合后，官方分工大致是 ：

• 豆包工作 / 豆包工作伙伴：面向员工的 Agent 协作层，可在飞书群、文档、会议、知识库里调用；支持生成/改 Word/Excel/PPT/网页/应用，也可操作电脑、多智能体协作、云端持续跑长任务。

• 飞书 8.0：作为协作与上下文承载平台，向 Agent 开放群聊、文档、多维表格、日历、会议、云盘、审批等；通过 CLI 向 Agent 开放功能点从 2026 年 3 月的 247 个增至 767 个。

• 火山引擎方舟：豆包大模型推理、Embedding、Agent 工具链、算力；开发者走 Ark API/SDK，不直接绑飞书 UI。

• 飞书开放平台 + lark-cli：把飞书能力做成 API、事件、SDK、命令行，供自研 Agent 或第三方编排调用。

注意：飞书历史上有「智能伙伴/Aily/飞书妙搭/集成平台(AnyCross)」等入口，和「豆包工作伙伴」不是完全同一产品。企业落地时要按“用原生豆包工作”还是“自建飞书机器人+豆包模型”两条路分开评估，不要混为一谈。

二、总体集成架构（数字员工可落地的三种形态）


员工/群/文档/会议
      ↓ 事件/消息/文件
飞书开放平台 ──┬── 原生豆包工作伙伴（托管Agent，账号互通，按用户权限读上下文）
               ├── Aily/智能体 OpenAPI（自建或低代码智能体，可被服务端/用户调用）
               └── 自建企业应用 ── 事件订阅/长连接 ── 后端服务
                                          ↓
                          编排层（工作流/DeerFlow/方舟Agent/MCP）
                                          ↓
                          豆包模型（火山方舟 Chat/视觉/长上下文）
                                          ↓
                          lark-cli / 飞书服务端API 回写消息/文档/表格/任务/审批


核心不是“接一个大模型”，而是四层都要通：身份鉴权 → 上下文读取 → 推理/工具调用 → 回写飞书并留审计。

三、飞书侧底层能力梳理

1. 应用形态与凭证

飞书开放平台支持机器人、网页应用、小组件；自建/商店应用两套。 凭证体系：

• tenant_access_token：应用身份，后台任务、机器人发消息、写表格、同步通讯录用；权限受应用被管理员授予的 scope 与应用数据范围限制。

• user_access_token：代表具体用户，读该用户有权限的文档/日历/邮件；做“代用户操作”用。

• app_id/app_secret：自建应用基础凭证；配合 IP 白名单、权限审批、事件加密。

权限分“应用身份权限”和“用户身份权限”两类，管理员按 scope 等级设免审/人工审。 多维表格、文档、审批、通讯录各自有独立 scope，不是给个 app_secret 全通。

2. 核心 OpenAPI 域（数字员工最常用）

飞书服务端总计 2500+ 标准 API， 数字员工相关重点：

• 消息/群组：发文本、富文本、图片、文件、卡片；建群、拉人、读群信息；卡片回调做交互。

• 事件订阅：im.message.receive_v1 等；支持 HTTP 回调或 SDK 长连接（WebSocket），本地开发用长连接更省事。

• 云文档/知识库：建文档、读写富文本、搜索、权限、归档；知识库节点/空间成员管理。

• 多维表格 Bitable：app_token/table_id 定位；记录增删改查、字段/视图、批量写入；做工单/周报/监控表回写主库。

• 电子表格：单元格读写、公式、样式。

• 日历/会议：日程创建、忙闲、视频会议录制/纪要（配合智能会议纪要）。

• 审批 v4：外部审批定义、实例同步、Bot 消息、状态查询；approval/v4/external_approvals、external_instances、instances/search、status_changed_v4 事件。

• 通讯录：部门/用户同步、入转调离、组织口径给 Agent 做路由。

• 任务/邮箱：待办闭环、邮件草稿/发送（敏感，需单独 scope）。

3. 智能体专用 OpenAPI（Aily/团队智能体）

如果走飞书智能体而不是纯自建机器人，Aily 提供对话型 OpenAPI：

• 鉴权：user_access_token（代表用户）或 tenant_access_token（应用身份，智能体需开启应用可调用）。

• Scope：aily:agent_chat:write（发起/管理会话）、aily:agent_chat:read、aily:agent_attachment:write（传文件）、aily:agent_artifact:read（拿产物）、aily:agent_visibility:read。

• 资源模型：agent_id → session_id → agent_chat_id，支持多轮、附件、产物隔离；应用身份下附件/产物按应用+session 隔离，用户身份下按用户隔离。

适合“已有飞书智能体，外部系统触发它做摘要/写回”的场景。

4. 飞书 CLI（lark-cli / 官方 Agent CLI）

这是飞书做 Agent 执行层的关键，不是玩具。

• 官方开源 @larksuite/cli（Go、MIT、npm 分发），定位 “built for humans and AI Agents”。

• 覆盖域：IM、日历、云文档、云盘、多维表格、电子表格、任务、知识库、通讯录、邮箱、视频会议，约 11 域、200+ 精选命令、19 个 Agent Skills，底层可直连 2500+ raw OpenAPI；输出 json/pretty/table/ndjson/csv，方便 Agent 解析。

• 三层命令：Shortcuts（人用，如 +agenda）→ API Commands（语义化）→ lark api（原始调用）。

• 安全模型：不模拟点击 UI，只封装 OpenAPI；权限边界与开放平台应用一致，tenant/user 身份可切（--as bot/user），支持 dry-run。

• 8.0 后飞书通过 CLI 向 Agent 开放功能点 247→767，意味着很多“建任务、改表格、读纪要、排日程”可直接用命令而非自己拼 HTTP。

对数字员工的价值：把“模型决策”和“飞书执行”解耦——Agent 出计划，CLI 按已授权 scope 执行，审计、限权、回滚都比让模型直接调原始 HTTP 更可控。

5. 低代码/集成层

• 飞书集成平台 AnyCross：系统对接、数据流通，少写代码。

• 飞书妙搭：轻量业务系统/AI 搭建；多维表格+自动化可做“半代码数字员工”。

• 卡片+机器人+工作流：审批、提醒、表单回写不需全量开发。

四、豆包 / 火山侧能力梳理

豆包作为模型与 Agent 能力，主要走火山引擎方舟：

• 推理 API：豆包系列对话模型、长上下文、视觉/多模态、Seed/Pro 等不同接入点；方舟提供模型接入点（endpoint），AK/SK 调用，部分兼容 OpenAI 协议格式，方便用 openai SDK 改 base_url 接。

• Ark CLI / 方舟项目：开通方舟→企业项目→AK/SK→CLI 初始化 Agent/调试；agent.yaml 声明模型、tools、skills、MCP。（第三方教程里的 ark cli、fangzhou cli 名称随文档版本变化，以火山方舟当前控制台为准。）

• Agent 工具链：方舟可挂 MCP、联网搜索、代码执行、文件处理；与飞书集成时在 agent 配置里放“飞书 MCP/CLI 连接器”或后端 tool。

• 开源编排：如 DeerFlow 可配豆包模型+飞书机器人渠道，适合深度调研/长任务/多步执行。

• 企业安全口径：豆包工作沿用飞书用户身份与对象权限，不主动扫全量私有文档，未经授权不用于基础模型训练，会话/记忆加密、租户密钥隔离；DLP/水印/行为审计按场景开通。

不建议信“飞书里有个统一 /ai_assistant/v1/invoke 豆包接口”这类二手教程；企业接豆包优先走火山方舟正式 endpoint，飞书内用户交互走豆包工作/自建机器人。

五、四种落地模式（按开发量从低到高）

模式 A：纯原生豆包工作伙伴 + 飞书 8.0
• 适用：已买飞书+豆包工作、要快速让员工在群/文档/会议里用 Agent。

• 做法：管理员开工作伙伴、按用户授文档/知识库/群上下文；配置自动化任务、工作小队、回写文档/表格/任务。

• 优点：不改代码、权限继承飞书、审计由平台出。

• 缺点：深层定制工具、对接内部业务系统要靠飞书开放能力或中间件。

模式 B：飞书自建机器人 + 火山方舟豆包
• 适用：知识问答、工单摘要、告警问答、表格填充。

• 技术栈：飞书自建应用→机器人+事件（长连接/HTTP）→后端 FastAPI/Node→方舟 chat completion→lark-cli/OpenAPI 回写。

• 最小权限：im:message、im:message:send_as_bot、bitable 只读/写指定表、doc 只读；模型只拿脱敏上下文。

• 示例链路：群 @bot → receive event → 取近 50 条消息+指定文档片段 → 方舟摘要 → 写多维表格待办 → 发卡片。

模式 C：Aily/智能体 OpenAPI + 豆包后端
• 适用：要把“飞书智能体”当服务被其他系统调用，或做多智能体协作。

• 做法：在飞书建智能体，开 aily:agent_chat:write 等 scope；后端用 tenant/user token 发会话、传附件、拉产物；智能体内部工具指向方舟豆包+MCP。

• 优点：会话/产物/可见性由飞书管；适合把“招聘初筛、合同摘要、周报”封装成可调用服务。

模式 D：lark-cli 驱动的执行型数字员工
• 适用：长任务、批处理、CLI/CI/Agent 编排，如“每晚拉会议纪要做待办、同步表格、建日历、发邮件草稿”。

• 做法：Agent（方舟/DeerFlow/自研）生成计划→调 lark-cli 命令（dry-run 先验证）→实际写飞书；用 tenant token 跑批量、用 user token 跑“代某员工”的操作。

• 优点：执行层标准化、输出机器可读、权限不超开放平台；比让模型手拼 curl 安全。

六、权限、安全、审计（企业必做）

1. 最小 scope：机器人默认只给收消息+按指定群发卡片；读文档按知识空间授权；写表格只给目标 app_token，不给全租户 bitable。
2. 身份分离：
   • 后台同步/批量写：tenant_access_token + 独立服务账号；

   • 代用户读私聊/个人日历：user_access_token，且用户显式授权；

   • 豆包工作原生任务：走当前用户飞书权限，不提权。

3. 数据边界：不把全量群聊、全量合同、薪酬、未公开财报授给 Agent；敏感字段在取上下文阶段脱敏，模型只看到 task-relevant 片段。
4. 审批与人工兜底：发外部邮件、删文档、批量改审批流、通知>50 人等“高不可逆”动作加人工确认；AI 只起草。
5. 限流降级：飞书 API 做超时/重试，QPS 留余量；模型服务异常时切规则引擎/人工队列，不静默丢任务。
6. 审计：飞书应用权限审批记录、CLI 操作日志、Aily 会话日志、方舟调用日志、数据出域记录统一留痕；DLP/水印按文档域开。
7. 密钥：app_secret、方舟 AK/SK 进密钥管理，不进代码；飞书应用开 IP 白名单；CLI 机器按主机绑定。

七、典型场景映射到接口（可直接排开发）

• 会议纪要→待办：会议事件/纪要权限 → 方舟摘要 → 创建任务 API / 多维表格写待办 → 群卡片分配责任人。

• 客户群摘要：按指定群订阅消息 → 时间窗抽取 → 豆包摘要+情感/商机标签 → 写 CRM 中间表/飞书表格 → 每日卡片。

• 审批自动初审：审批实例事件 → 取表单+关联文档 → 方舟按规则出“通过/补材料/转人工”建议 → 回写审批评论或外部系统，最终审批人点确认。

• 知识库问答：知识空间授权 → 方舟+向量检索（企业知识入库） → Aily 或自建机器人回答 → 引用文档链接，按用户权限过滤。

• 经营报表填数：多维表格读取 → 内部系统通过集成平台/API 取数 → 方舟生成解读 → 回写表格+发日历周报任务。

• 跨系统工单：飞书收消息 → 方舟分类 → 调业务系统 API → lark-cli 建任务/改状态/发进度。

八、选型结论（给你一个判断口径）

• 要“员工马上用、少开发、权限继承好”：原生豆包工作伙伴 + 飞书 8.0，配合知识库治理。

• 要“把豆包嵌自有业务、可控 Prompt/工具/MCP”：飞书自建机器人/网页应用 + 火山方舟，执行层用 lark-cli 或服务端 SDK。

• 要“智能体作为内部服务被多系统调用”：Aily OpenAPI 封装，后端接方舟。

• 要“长任务/电脑操作/多智能体”：豆包工作+云电脑/工作小队，但必须把飞书回写动作限制在 CLI/API scope 内，不做无审计 UI 自动化。

• 强合规行业：user 身份优先、全量数据不出知识空间、DLP/水印/审计全开、模型训练授权书面确认。
