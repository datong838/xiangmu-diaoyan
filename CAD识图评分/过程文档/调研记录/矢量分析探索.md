核查，**有个必须主动说的风险：我一直在用的 PyMuPDF 是 AGPL-3.0**。先讲三层技术栈，最后说这个。

## 一、实际用到的技术栈（实测确认）


| 层        | 技术            | 版本     | 许可                           | 用途                               |
| -------- | ------------- | ------ | ---------------------------- | -------------------------------- |
| **矢量解析** | **PyMuPDF**   | 1.28.2 | ⚠️ **AGPL-3.0 / Artifex 商业** | `get_drawings()` 提线宽/坐标/dash     |
| 栅格化      | pdf2image     | —      | MIT                          | PDF→图像（R2V 前提）                   |

| PDF 体检   | poppler-utils | —      | GPL                          | `pdffonts` `pdfinfo` `pdfimages` |


**关键区分**：上面这些是**成熟开源库**，但**我做的事没有现成体系**——

我自己写的算法（无开源体系支撑，纯临时脚本）：

- **共线聚类还原短划序列**（发现 T02 的 13 段长画 32.4pt + 间隙 5.4pt）
- **等腰三角筛选器**（找锥度符号，**失败**了，400+ 候选无法识别）
- **线宽游程测量**（栅格法，已用 T05 真值标定，误差 ≤5%）
- **矢量差分**（T01 因幅面不同失败，T05 成功）

这四类**没有对应的开源库**，因为它们是本项目特有的判据需求。

## 二、CAD 工程图矢量解析的开源生态（回答你的核心问题）

**有体系，而且比我现在用的强得多**——但前提是拿到 **DWG/DXF**，而不是 PDF。


| 项目                     | 许可             | 能力                                                    | 局限                           |
| ---------------------- | -------------- | ----------------------------------------------------- | ---------------------------- |
| **ezdxf**              | **MIT**        | DXF R12–R2018 读写，**实体级访问**：LINE/TEXT/DIMENSION/图层/线型  | ❌ 不能转 DWG                    |
| **LibreDWG**           | GPLv3          | DWG 读写（R2000–R2010 较好），含 `dwglayer` 列图层、`dwggrep` 搜文字 | ⚠️ R2010+ 部分实体读不了；GPLv3 有传染性 |
| **ODA File Converter** | 免费，**非会员仅非商用** | DWG↔DXF 批量转换，Win/Mac/Linux                            | 商用需 ODA 会员                   |
| QCAD / LibreCAD        | GPL            | 完整 CAD 桌面端                                            | 不是库                          |


**这套体系能直接解决我们卡住的问题**：


| 当前卡点（PDF 层）                   | 用 ezdxf/LibreDWG 后                          |
| ----------------------------- | ------------------------------------------- |
| 文字转曲，`Ra 6.3`/`H7`/`1:10` 读不到 | ✅ TEXT/MTEXT 实体**直接读字符**                    |
| dash 全空，线型判不了                 | ✅ **LINETYPE 字段直接写明** CENTER/PHANTOM/DASHED |
| 尺寸数值读不到                       | ✅ DIMENSION 实体含**实测值+公差+公差带代号**             |
| 图层丢失                          | ✅ 图层名可区分中心线层/轮廓层                            |


**这也印证了我一直说的：DWG 是突破当前瓶颈的唯一路径。** 现在可以补充一句——不只是"能突破"，而是**有成熟的 MIT 许可库（ezdxf）可以直接用**，不需要自己造轮子。

## 三、⚠️ 必须提醒的许可风险：PyMuPDF 是 AGPL

我实测确认：

```
pymupdf 1.28.2  License: Dual Licensed - GNU AFFERO GPL 3.0
                 or Artifex Commercial License
```

**这对你们意味着什么**：

- AGPL 的传染性比 GPL 更强——**SaaS 场景下用户上传 PDF 也算"分发"**
- 如果这套判据库最终要作为**闭源商用产品**（或对外服务），**直接用 PyMuPDF 有合规风险**
- Artifex 提供商业许可，是需要付费买的

**这个风险我之前八轮都没提**，因为我一直在解决技术问题，没检查自己所用工具的许可——而我却在报告里反复提醒你们注意 GLM-OCR 的许可矛盾。**这是双重标准，应当指出。**

**替代方案**（避开 AGPL）：


| 库              | 许可    | 矢量能力                                              |
| -------------- | ----- | ------------------------------------------------- |
| **pdfplumber** | MIT   | 基于 pdfminer.six，字符级+线条，表格强，但**向量图元不如 PyMuPDF 直接** |
| pypdf          | BSD   | 弱，无 table API                                     |
| **pypdfium2**  | BSD-3 | PDFium 绑定，渲染快，可替代渲染环节                             |
| pdfminer.six   | MIT   | 底层 content-stream 解析                              |


**务实的建议**：

1. 若仅**内部研究/自用** → PyMuPDF 继续用，无问题
2. 若要**产品化/对外交付** → 评估 pdfplumber（MIT）能否覆盖核心需求，或买 Artifex 商业许可
3. **最优解仍是拿 DWG** → 转 DXF 后走 **ezdxf（MIT）**，从源头绕开 PDF 解析层的许可与能力双重限制



## 四、一句话总结

**我用的库都是开源的，但"矢量解析"这个动作本身没有现成体系**——线型还原、符号定位这些是我临时写的。真正的成熟体系在 **CAD 侧（ezdxf/LibreDWG/ODA）**，不在 PDF 侧。**拿到 DWG 后走 ezdxf，比在 PDF 层继续打磨要划算得多**，而且 MIT 许可干净。
