## 一、符号编码层方案

### 1.1 符号等价类表（已确认三组，可直接入库）

| 语义 | 等价码位 | 位置约束 | 出现次数 |
|---|---|---|---|
| **直径** | ⌀ U+2300 / Ø U+00D8 / ∅ U+2205 / φ U+03C6 / Φ U+03A6 | **紧邻尺寸数字之前** | 3 次 |
| **深度** | ↓ U+2193 / ↧ U+21A7 | 数字之前 | 1 次 |
| **数量前缀** | × U+00D7 / * U+002A | 数字之前 | 2 次 |

**⚠️ 三条使用约束**

1. **必须绑定位置约束**。φ 离开"数字前"会变成相位角/磁通量/黄金分割率——电气图纸上会误判。等价类不能无条件合并。
2. **五个直径字符都不是标准符号**。GB/T 与 ISO 规定的标准是 **⌀ U+2300**；Ø 是丹麦语字母、φ 是希腊字母、∅ 是空集符号。
   - 工程惯例上等价 → 判"对"无误
   - 判据库**引标准条款时只能写 ⌀**
3. **`×` 比 `*` 更规范**。GB/T 4458.4 表 A.1 示例（如 `4×φ8 EQS`）用 `×`；`*` 是 ASCII 替代写法。

### 1.2 已确认归类（可直接引用）

| 标注 | 语义 | 核实状态 |
|---|---|---|
| `4×M4 ↓8` | 4 个 M4 粗牙螺纹孔，螺纹**有效深度** 8mm | ✅ 人工核实为深度（非埋头孔） |
| `4*M4` | 4 个 M4 螺纹孔 | ✅ 与 `4×M4` 等价 |
| `Ø142 +0.028/+0.003` | 直径 142，区间 142.003–142.028 | ✅ 语义等价，仅分隔符差异 |
| `Ø60 +0.03/0` | 直径 60，区间 60.000–60.030 | ✅ 语义等价 |
| `54 0/-0.2` | 长度 54，区间 53.8–54.0 | ✅ |
| `28 +0.05/0` | 长度 28，区间 28.000–28.050 | ✅（**曾误读为 26**） |

### 1.3 待人工核实的形态歧义（🔴 高优先级）

| 歧义对 | 差异 | 后果 | 状态 |
|---|---|---|---|
| **↓ 深度 vs ∨ 埋头孔** | 箭头 vs V 形三角 | `8` 从"深度 8mm"变成"锥形沉孔直径 8" | ✅ 已由人工确认为深度 |
| 沉孔 ⊔ vs 埋头孔 ∨ | 方框 vs V 形 | 加工刀具完全不同 | ⏳ 待核 |
| 斜度 ∠ vs 锥度 △ | 单向楔形 vs 对称楔形 | 标注对象不同 | ⏳ 待核 |

**GB/T 4458.4 表 A.1 序号 9/10/11**：深度 = ↓；沉孔或锪平 = ⊔；埋头孔 = ∨。

**方案**：建立「符号形态—码位—语义」对照表，**形态列留空待人工核实**，码位与等价类由程序填。每图入库前跑一遍形态校验。

### 1.4 一个已验证的失真源

`4×M4 ↓8` 的**图像描述写成了「▽8」（三角）**，实际是箭头。**连描述环节都会失真**。

**方案**：真值集增加「**形态描述来源**」字段，取值：
- `AX描述` — 可信度**最低**
- `人工核实` — 可信度最高
- `矢量判定` — 可信度中

## 二、尺寸解析层方案

### 2.1 三元组归一化（核心规则）

**禁止按字符串比对。** 统一归一为三元组：

```
canonical = (基本尺寸, 上偏差, 下偏差)
```

| 原始串 | 归一结果 |
|---|---|
| `Ø142 +0.028/+0.003` | (142.0, +0.028, +0.003) |
| `Ø142 +0.028 +0.003` | (142.0, +0.028, +0.003) ← 与上式**相同** |
| `Ø60 +0.03/0` | (60.0, +0.03, 0.0) |
| `φ60+0.03 0` | (60.0, +0.03, 0.0) ← 与上式**相同** |
| `54 0/-0.2` | (54.0, 0.0, -0.2) |

**分隔符等价**：`/`、空格、`^`、`,`、括号 —— 全部丢弃。

**数值处理**：统一转 float 比对，避免 `0.028` vs `.028` 差异。

### 2.2 正则解析规则（🔴 必须，不能按空格分词）

**触发问题**：`φ60+0.03 0` 中 `60` 与 `+0.03` **无空格**，
`"φ60+0.03 0".split(" ")` → `["φ60+0.03", "0"]` → **基本尺寸解析失败**。

**推荐正则**：

```python
r'(?P<sym>[⌀Ø∅φΦ]?)\s*(?P<base>\d+(?:\.\d+)?)\s*'
r'(?P<up>[+-]?\d+(?:\.\d+)?)?\s*[/^ ,]?\s*'
r'(?P<low>[+-]?\d+(?:\.\d+)?)?'
```

**补充锚点规则**：基本尺寸后紧跟 `+` 或 `-` 时，**从符号处切分**——这是无空格场景的可靠分隔标志。

### 2.3 偏差符号规则

| 情况 | 写法 | 说明 |
|---|---|---|
| 上偏差为正 | `+0.028` | **`+` 不可省略** |
| 下偏差为负 | `-0.2` | `-` 不可省略 |
| 偏差为零 | `0` | **写 0，不加正负号** |

**⚠️ 未核实项**：「偏差为零必须写 0、不加正负号」**我未在 GB/T 4458.5 原文定位到逐字条款**。
- 你们那份 4458.5 是"扫描图+OCR 文字层"（7/8 页有文本、含乱码）
- 该条已**第三次被引用**，若判据库要引条款号 → **必须人工核 4458.5 原图**

**"小数点对齐"存疑**：若严格按通用要求，`0.05` 对应的下偏差理论上该写 `0.00` 而非 `0`。**同样未核实，不判定违规。**

### 2.4 尺寸类别必须独立记录

同为 `54`：

| 写法 | 语义 |
|---|---|
| `54` | 长度 54 |
| `⌀54` | 直径 54 |
| `R54` | 半径 54（对应直径 108） |

**数字相同，语义可差 2 倍。** 真值集**必须**记「尺寸类别」，不能只记数字。

## 三、真值集建设方案

### 3.1 字段规范（建议 8 字段）

```
必填：
  基本尺寸        54 / 142 / 60
  尺寸类别        线性长度 | 直径 | 半径 | 球面 | 角度 | 弧长
  上偏差          +0.05  /  0  /  -0.2
  下偏差          0      /  -0.2
  合格区间        自动计算
  尺寸类别        见上
推荐：
  DXF实体         DIMENSION | MTEXT | TEXT
  原始串          54\S0^-0.2;   （DXF 实际存储）
  形态描述来源    AX描述 | 人工核实 | 矢量判定
  提取异常        +号是否丢失 / 符号码位 / 分隔符
```

**`原始串` 为什么重要**：`54 0/-0.2` 是**线性化结果**，DXF 里实际是：

| 实体 | 原始形态 |
|---|---|
| MTEXT | `54\S0^-0.2;`（`\S`=堆叠，`^` 分隔上下） |
| DIMENSION | 基本尺寸、上偏差、下偏差**分字段存储** |

**回读时必须按实体类型分别解析**——用 MTEXT 正则套 DIMENSION 会读不到。

### 3.2 交叉校验流程（🔴 已验证有效）

**触发问题**：我把 `28` 误读成 `26`，而你的图注尺寸列表里**只有 28、没有 26**。
只要拿读数与列表对一下就能拦住，但我没做这一步。

**强制规则**：**任何从图上读出的数值，必须先与同一来源的其它信息交叉校验，再写入真值集。**

可用校验源（按优先级）：
1. **DXF 实体实测值**（最强）
2. 图注/尺寸清单
3. 相邻尺寸几何合理性（各段之和 = 总长）

### 3.3 真值源优先级

```
DXF/DWG 实体  >  PDF 文本层  >  OCR  >  人工读图  >  AI 读图
```

**AI 读图（包括我）只能作为"待校验候选"，不能作为真值。**

## 四、数据源方案

### 4.1 为什么 PDF 这条路走不通（已实证）

| 限制 | 实测证据 |
|---|---|
| 图纸无文本层 | 10 张正误图 `get_text()` 全 0；文字转曲 |
| dash 为空 | 全部 `[] 0` 或 `None`，无一例外 |
| **SHX 字体丢符号** | `%%c16` 用 SHX 导 PDF → 符号丢失，只剩 `16` |

**最后一条是决定性的**：不是 OCR 不行，**是导出时就没写进去**。SHX 文字在 PDF 里是描边不是字符，压根不可搜索。

### 4.2 DXF + ezdxf 方案（⏳ 待拿到文件）

| 当前卡点 | 用 ezdxf 之后 |
|---|---|
| 文字转曲读不到数值 | ✅ TEXT/MTEXT 直接读字符 |
| dash 全空判不了线型 | ✅ **LINETYPE 字段直接写明** CENTER/PHANTOM/DASHED |
| 尺寸读不到 | ✅ DIMENSION 含实测值+公差+公差带代号 |
| 图层丢失 | ✅ 图层名可区分中心层/轮廓层 |

| 项目 | 许可 | 能力 |
|---|---|---|
| **ezdxf** | **MIT** ✅ | DXF R12–R2018，实体级访问 |
| LibreDWG | GPLv3 | DWG 读写，R2010+ 部分受限 |
| ODA File Converter | 免费但**非会员仅非商用** | DWG↔DXF 批量转换 |

**推荐路径**：DWG →（ODA 转换）→ DXF →（ezdxf，MIT）→ 判据验证。

**可一次性解锁**：T02-5、T04-3（线型 100% 程序化）+ 应用层尺寸判据。

## 五、OCR 方案

### 5.1 三条路线的优先级（已澄清）

```
第 1 优先：买正版文本版     ← 直接消灭 OCR 需求
第 2 优先：双源校验         ← 防 VLM 幻觉
第 3 优先：换 OCR 引擎      ← 收益最小
```

**为什么换引擎不是最优解**：我遇到的误识（网认→默认、寺除→去除、目邻→相邻、圆锥难度→圆锥锥度）是**术语级错误**，不是字符级错误。再强的传统 OCR 也会犯。

### 5.2 引擎选型结论

| 用途 | 方案 |
|---|---|
| **主力** | **PaddleOCR-VL-1.6**（0.9B，Apache 2.0，可本地部署） |
| 交叉验证 | GLM-OCR（95.22，MIT，**许可矛盾待核**） |
| 独立验证 | Mistral OCR 4 API（93.07）—— **仅用脱敏页**，数据出境 |

**⚠️ 两条硬约束**
1. **OmniDocBench 的 9–10 类文档里没有机械制图/工程标准**。96+ 分是"文档解析"分（text/formula/table/reading order），**不等于术语级准确**。
2. **VLM 是"预测"不是"识别"**——可能生成看起来合理、原文不存在的条款号。**对判据库是致命的。**

### 5.3 双源校验（必须）

**绝不允许 VLM 单输出直接进判据库。** 关键条款一律双源确认。

**现成金标准集**（可直接用于 POC）：
- GB/T 131 物理页 13–22（已知 8 处误识）
- GB/T 4457.4 乱码页

### 5.4 标准 PDF 验货（已交付脚本）

```bash
pdffonts "标准.pdf"        # 有字体名=文本版；空=扫描件
```

或运行已交付的 `标准PDF文本层检测.py`（区分：原生电子版 / 扫描图+OCR层 / 纯扫描件 / 矢量图转曲）。

**⚠️ 判据不止"有没有文字层"**——曾误判 7 份为"文本版"，实际只有 4 份是原生排版。真正判据是**字体是否嵌入** + **是否整页扫描图** + **实际乱码检测**。

## 六、判据库架构方案

### 6.1 四层分层（防止引用错误）

| 层 | 内容 | 示例 |
|---|---|---|
| **读取层** | 图上实际是什么 | 需 DXF 或人工 |
| **出处层** | 标准原文怎么说 | `15754-2025 §4` |
| **命题层** | 判据是否成立 | 通过/存疑/否决 |
| **应用层** | 该图是否违规 | 绝大多数**无法判定** |

**关键**：32 条中命题层通过 21 条，但**应用层仅 T05-5 一条可确认**。分层可避免把"原文支持"误当成"该图违规"。

### 6.2 判据三级来源（以孔/轴大小写为例）

| 层级 | 依据 | 状态 |
|---|---|---|
| **定义层** | GB/T 1800.1-2020 §4.1.2.5 + §4.2.1（孔大写/轴小写） | ✅ 原生文本层，零 OCR 风险 |
| **图例层** | GB/T 4458.5 图 1 `65k6` / 图 2 `Ø65 H7` | ✅ OCR |
| **条文层** | 4458.5 §5.1 | ❌ **只规定分数位置，不定义大小写** |

**规则**：**不得**引 4458.5 §5.1 作为大小写定义依据。

### 6.3 版本溯源口径（客户已拍板）

| 口径 | 执行 |
|---|---|
| 按**最新版本**评判 | 现行版优先 |
| 新版本第一、老版本第二 | 两级表述 |
| **不判定老标准"错误"** | 只指出版本出处 |
| 对错由评判人决定 | AI 不拍板 |

**⚠️ 教训**：曾用"源自同一 ISO"推断"各版一致"，被 15754-2025 前言推翻（明载"更改了锥度的图样表示"）。
**规则：版本一致性必须读到原文，不能用采标关系反推。**

## 七、工程实现方案

### 7.1 栅格转矢量（R2V）—— 已标定

| 对象 | 矢量真值 | 栅格实测 | 误差 |
|---|---|---|---|
| T05 正确版 | 2.04 pt | 2.000 pt | 2.0% |
| T05 错误版 | 0.84 pt | 0.800 pt | 4.8% |

**方法可信**，可用于纯扫描标准的图形本体测量。

**已失败两项**（诚实标注）：
- 131 图 1 的 60° V 形符号：Hough 检出 409 条线段，**60° 不等长配对 = 0**
- 锥度符号定位：等腰三角筛选器单图 **400+ 候选**，无法识别（45° 倒角也符合）

**锥度符号正确路径**：先定位**指引线+基准线**（§5.2 明载必带指引线），再反查符号——不要盲搜三角形。

### 7.2 线型判定（结论已修正）

**原判断（错）**：「dash 为空 → 线型永远判不了」
**修正后**：dash 为空但线型**被展平为短划序列**，信息保留在几何周期里。

**实测证据**（T02 端盖）：13 段共线、长画 32.4pt、等距间隙 5.4pt、线宽 0.72pt。

**三个障碍**（未解锁）：聚类噪声 / 无构造数值基准 / 点画线的"点"极短易丢。

### 7.3 许可风险（⚠️ 待决策）

| 库 | 许可 | 风险 |
|---|---|---|
| **PyMuPDF** | **AGPL-3.0 / Artifex 商业** | SaaS 场景有传染性 |
| pdfplumber | MIT | 矢量能力较弱 |
| pypdfium2 | BSD-3 | 可替代渲染 |
| ezdxf | MIT | 干净 |

**这是我自查发现的双重标准问题**——我反复提醒你们注意 GLM-OCR 许可，却没检查自己所用工具的许可。

**建议**：仅内部研究 → 继续用；产品化 → 换 pdfplumber 或买 Artifex 许可；**最优仍是走 DXF + ezdxf**。

## 十一、外部建议评估：Llama 3.3 + CAD-Assistant

> 来源：第三方建议「机械二维 CAD 图纸检测识别与评分，可看 Llama 3.3 系列 + CAD-Assistant」
> 本节按"核实事实 → 判断适配性 → 提炼可借鉴部分"三步评估。

### 11.1 🔴 三处硬不匹配（核实后确认）

| # | 问题 | 核实结果 |
|---|---|---|
| **1** | **Llama 3.3 不能看图** | Meta 官方定位："Built for **text-based** use cases"。Llama 3.3 = 70B **纯文本**单一模型（非"系列"）。视觉能力在 **Llama 3.2 Vision（11B/90B）** 与 **Llama 4**（Scout/Maverick）。**图纸是图像，3.3 直接不可用。** |
| **2** | **CAD-Assistant 任务方向相反** | ICCV 2025 论文。它是**生成 FreeCAD 代码去"建/改"模型**的**设计辅助**智能体（planner + FreeCAD Python API + 7 个工具）。我们要的是**审查既有图纸是否符合国标并评分**——是"检查"不是"创作"，**无评分/审查组件**。 |
| **3** | **许可与合规双重阻断** | ① GitHub 明载 **Attribution-NonCommercial** → **不可商用**<br>② 其 planner 是 **GPT-4o**，`config.json` 需填 **OpenAI API key** → **数据出境**<br>与我们"采标标准涉 ISO 版权须私有化"的硬约束**直接冲突** |

> **补充**：建议本身自相矛盾——"开源本地部署"与"CAD-Assistant"不兼容，后者依赖闭源云 API 作 planner。

### 11.2 ✅ 但有两处值得借鉴

**① 工具增强范式（planner 生成代码 → 环境执行 → 反馈迭代）**

`planner → 生成 Python 代码 → 在环境中执行 → 返回结果 → 修正下一步`

这个闭环对我们有价值：可让模型**生成 ezdxf 脚本**去查 DXF（而非让它"看图猜"），**用确定性工具保证精度**。这与我们已定的"精度靠结构化数据"方向一致。

**② One-shot 视觉范例（来自 BlueprintSymVL 基准）**

Chalmers/Eindhoven 2025 年研究：查询时**给模型一个符号的视觉样例**，可"消除对不可靠先验知识的依赖"。

**这直接治我们的符号码位病**——⌀/Ø/φ 混淆，与其让模型猜，不如**给它看符号原图**。建议引入 L2/L4c 层。

### 11.3 🔴 一条对我们不利但必须知道的证据

**BlueprintSymVL**（Results in Engineering 2025）测了 GPT-4o、Gemini 2.5 Pro、InternVL 2.5 78B、Qwen2.5-VL 72B 在**工程蓝图符号识别**上的表现，结论原文：

> 「failure modes include a notable **degradation in cluttered environments**, confusion when faced with **visually similar distractors**, and a concerning **propensity to hallucinate symbols**」
> 「current VLMs are **not yet suitable for autonomous deployment** in blueprint analysis and are best integrated into **human-in-the-loop** workflows」

**这从第三方实证角度印证了我们一直坚持的两条**：
- VLM 会**幻觉符号** → 判据库绝不能采信 VLM 单输出
- 最佳定位是 **human-in-the-loop**，不是自动部署

### 11.4 若确需开源视觉引擎（备选清单）

| 模型 | 备注 |
|---|---|
| Qwen2.5-VL 72B | BlueprintSymVL 已测 |
| InternVL 2.5 78B | BlueprintSymVL 已测 |
| Llama 3.2 Vision 90B | Llama 系唯一有视觉的 3.x |
| Llama 4 Scout / Maverick | 原生多模态 |

**但按 11.3 的证据，这些都不应作为判据库的唯一信源。**

### 11.5 结论

**该建议不采纳为技术路线**，理由：模型不能看图 + 任务方向相反 + 非商用许可 + 数据出境。

**采纳其中两点**：工具增强范式（模型生成代码调用 ezdxf）与 one-shot 视觉范例（符号识别给样例）。

**行业共识佐证**：CAD 垂直领域"工程方法的收益远大于换模型的收益"；实测迭代中纯图像路线全部失败，**胜出方案是 DWG→DXF 结构化提取 + 截图校正**——与我们已定方向一致。
