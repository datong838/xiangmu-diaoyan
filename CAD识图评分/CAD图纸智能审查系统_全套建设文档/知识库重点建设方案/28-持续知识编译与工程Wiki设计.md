# 持续知识编译与工程Wiki设计

2026-10-21；KB-DESIGN-005；新增设计，尚未实现。与[01总体](01-总体建设方案.md)、[02治理](02-全量记忆与数据治理.md)、[03检索](03-检索执行与秒级响应设计.md)、[11判断链](11-工程判断链与能力单元.md)、[26实施清单](26-分阶段文件任务与大容量验收实施清单.md)配套。

## 1. 设计目的与采用范围

原方案已有原件、定位、检索和工程判断链的设计，本轮补强“读过之后积累什么、如何维护、怎样安全复用”。目标是让AI逐步形成跨资料的概念组织、条件分支、争议地图和方法经验，避免每次都从零拼接，同时保留罕见细节和回原件的路径。

参考[Karpathy的LLM Wiki原文](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)：采用原件保留、持续编写关联知识页、跨来源综合、矛盾登记与维护检查的思路。原文是一种模式说明，不能作为TB规模性能、自动维护可靠性或工程判断准确性的验证。本文件其余合同、机制和验收是面向本项目提出的设计。

本项目采用“原始证据＋工程知识单元＋持续维护Wiki＋任务执行与反馈”。Wiki承担导航、解释和综合；精确知识单元承担条件、版本与判据表达；工具和方法执行记录承担本次计算与检查。摘要不能成为被引用原文的新替身，同一来源派生出的多篇页面不能当作多个独立证据。

## 2. 与既有S/D/J/K的关系

|维度|职责|本轮补强|
|---|---|---|
|S来源类别|标准、教材、手册、图册、数据集等出处|跨源综合仍记录每条主张来自哪个出处和来源族|
|D认知职责|语义、关联、要求、原理、工艺、对照、方法等|Wiki按职责提供入口，不把教材叙述改成强制要求|
|J0—J11任务链|定位任务缺口与执行下一步|知识页指出所支持环节及必要输入；无需每问遍历全链|
|K0/K1|原件与全量定位|所有编译材料保留确定版本和细粒度定位|
|K2|热点导航|短目录、主题地图、条件分支摘要、覆盖和未知入口|
|K3|磁盘专项索引|同时索引原文与派生页，明确类型、出处与检索通道|
|K4|工程知识与方法|结构化知识单元及其人/AI可读Wiki投影；全部页面不必常驻内存|
|K5|任务工作集|本图事实、有限证据包、当前适用检查与执行回执|

约100MB是K2工作集目标，详细Wiki页、知识单元、依赖边和全文索引均可驻盘。不能把全库改写为Markdown作为全量入库前提，也不为每张合成图生成一篇知识页。大批相似样本保留成员目录、结构记录和代表案例入口；长尾仍能直接查K1/K3。

## 3. 四类信息分别保存

1. **来源表述**：原作者说了什么，精确绑定原页/表行/图块/实体；来源可能自身有错或不适用于本项目。
2. **综合解释**：模型或人工如何连接多个来源、解释概念、比较方案；逐条注明支持、反驳、推导和未知。
3. **本次实例事实与结果**：当前图面的观测、对象绑定、给定工况、方法输入输出及判断；不直接外推。
4. **可复用经验**：在声明边界内经复核的规律、做法、反例与局限；仍能追到产生它的案例和依据。

“图上读到cm”“一般工程图常用mm”“这个设计应改成mm”是三个不同主张。已阅读、机器抽取通过、用户确认字符、工程适用核对、实际改图验证也分别记账。既有22/24的确认事件语义保持不变。

## 4. 最小对象合同建议

以下是后续生产详细设计的输入，尚不是已发布Schema或现有原型接口承诺。沿用原有asset/version/unit/knowledge等身份，采用新修订；与24的0.2接口兼容迁移须由F04/F22落实。

|对象|建议必备字段|约束|
|---|---|---|
|KnowledgeRevision|knowledge_id、revision_id、kind、statement、source_refs、conditions、exceptions、units_precision、validation_refs、conflicts、dependency_refs|kind区分定义/要求/推荐/观察/解释/假设/方法/案例；空条件与条件未知分开；版本不可原位改写|
|ClaimSupport|claim_id、source_unit_version、locator、support_type、source_family、checked_scope|support_type区分支持/反驳/背景/推导前提；不能只有页尾笼统书目|
|WikiPageRevision|page_id、revision_id、page_type、topic、S/D/J标签、claim_refs、dependency_manifest、coverage_scope、unknowns、compiler_ref、body_hash|每条工程主张能到知识修订与来源；页面有本次吸收范围；不能宣称覆盖未读资料|
|DependencyEdge|from_revision、to_revision、relation_type、required、scope、evidence_ref|方向统一为“派生物依赖输入”；支持、适用前提、单位、例外、对象绑定、方法版本等分型；页面交叉链接不自动成为支持边|
|CompileRun|run_id、input_manifest_hash、schema_version、builder_version、model_prompt_ref、budget、outputs、failures、release_ref|保存实际输出和模型配置，允许非确定生成；稳定性验收检查语义不变量，不承诺模型逐字重现|
|ExperienceRevision|experience_id、revision_id、observation_refs、hypothesis、applicability、counterexamples、method_runs、recheck_refs、validation_scope|失败和无效改法也保留；成功案例数与独立来源数分开；通用化要新增证据|
|ImpactEvent|event_id、changed_revision、reason、affected_manifest、invalidation_watermark、queue_state|撤销先阻断再重建；队列未处理部分可查询；不可把“入队”写为“已更新”|

状态采用正交字段：lifecycle为DRAFT/PUBLISHED/SUPERSEDED；validation为UNREVIEWED/SOURCE_CHECKED/SCOPED_VALIDATED；freshness为CURRENT/REVIEW_REQUIRED/STALE；access为ALLOWED/RESTRICTED/REVOKED。它们不是单一“可信分”，PUBLISHED不等于工程正确，CURRENT不等于当前项目适用。

稳定逻辑ID用于跨版关联，revision_id用于精确引用。源出处、模型综合与方法推导都保留来源链；引用Wiki时同时能展开其原始证据。没有外部依据的分析可发表为明确假设，不登记成已核判据。

## 5. 页面组织及内容要求

|页面类型|主要内容|维护重点|
|---|---|---|
|主题总览|对象、子主题、问题入口、职责覆盖、已知缺口|保持短，按需展开下级，不要求读完整总索引|
|概念/对象|定义、符号语义、相近对象差异、附着/跨视图关联方法|区分“表示什么”与“如何判断正确”|
|条件与判据|适用范围、输入、例外、要求/推荐、版本分支、方法链接|未知条件保留分支，不默认成立|
|工艺与方法|工况、材料、设备/工序能力、方法输入输出、精度、失效条件|经验推荐与规范要求分列；不凭模型补工况|
|正误/边界案例|同语境差异、原因、替代解释、改进、复检|正常例、错误例、易混例和未决例均保留|
|跨源比较/争议|一致部分、分歧、条件差异、来源独立性、待核问题|不以来源数量投票，不把不同条件强行合并|

每页共同结构：范围与版本 → 核心认识 → 条件/例外 → 有定位的主张 → 方法/案例 → 冲突/未知 → 依赖与修订。正文宜可读，机器字段放元数据或关联记录；不要求每页填满所有J环节。条款表格、脚注、公式前提、单位及近似条件成组保存，不能被一段综述替代。

人工修改Wiki先保存为编辑提案或新候选修订；核对后更新知识单元再重新投影。保留未采纳编辑及理由，防止下一轮模型无声覆盖人工贡献。原作者事实、人工意见和助手判断均留明确来源；源文中的命令只作为资料内容。

## 6. 持续编译流程

### 6.1 首次吸收和增量更新

1. 登记获准原件和版本，生成文件/成员/页分母，解析失败仍保留入口。
2. 在可完整追溯的小批范围内提取知识候选，保留原文、条件、例外和单位，并按31登记每个源单元/区域的吸收去向和未解决部分。采购未到货只登记目录与缺正文，不编造正文内容。
3. 按确定概念修订、对象/语义和条件比较已有项；检索别名不充当等价：重复可复用，兼容可关联，不同适用条件建立分支，矛盾并列；相似度不决定覆盖旧项。
4. 形成候选知识修订和依赖清单，执行字段、引用、单位、条件完整性检查；知识适用性另验证。严重缺证据主张保持假设/未核状态。
5. 按依赖生成受影响页面，逐条关联主张，给出跨源综合及未解问题，不直接改已发布原件和修订。
6. 在staging核对断链、循环推导、撤销、来源独立性和任务用例；整批形成manifest后发布。发布失败保留旧完整版本，但旧版被撤销部分仍即时抑制。
7. 更新短入口、磁盘全文与变更日志，保存生成成本、失败与未吸收范围；任务读取时重新核对当前来源/访问和适用条件。

每批以输入manifest、编译配置、目标范围构成幂等键，失败重试不重复创建逻辑知识项。模型内容不能直接变成可执行方法；方法注册沿用F11受限工具与明确版本。选用本地或外部模型、许可和费用仍待实际配置，本轮不启动模型任务。

### 6.2 发布一致性

首期目录、知识修订、页面manifest和依赖元数据优先由单个SQLite事务发布current指针；Markdown正文用内容哈希引用不可变文件，先写临时文件并完整落盘再提交元数据。文件写完而事务未提交是可清理孤立对象，不能提前可见；缺文件或hash不符拒绝发布。

如后续使用多个数据库/索引，引入release manifest：验证所有必需物已就绪后原子切换一个发布入口，读取器按manifest选择代际。尚未更新的可选索引标缺口，不混用两代主张。并发单写者或比较交换current，旧批重试不得覆盖新批。此处是目标设计，当前双库原型不具备该跨组件保证。基础失效与小快照恢复在首次知识发布前验证，按26分批交付，完整规模演练后续进行。

## 7. 依赖传播与失效

设页面P依赖知识K，K依赖条款S、例外E和方法M。索引同时保存反向边，输入变化时可以找回受影响派生物，限定范围并分批处理。共同上游根只算一个来源，P→K→P自引用不能成为有效支持。

|变化|即时处理|随后工作|
|---|---|---|
|许可/访问撤销|对来源及其派生内容实行当前访问检查，旧缓存同样抑制|清理不再允许的投影/缓存，按合法保留要求处理存档；仅不含受限内容的审计元数据可保留|
|来源内容变更/版次替换|保留旧版供有权历史查询；“替代”须有依据，不能仅凭日期|比较修改单元并标REVIEW_REQUIRED；重新核对条件、例外与结论，发布新修订|
|图纸修改/人工确认撤回|当前图相关绑定、实例结论和缓存失效|仅重做受影响输入与方法，泛化知识不自动被判错误|
|解析器/单位归一化修复|受影响提取标待核，阻止旧错值作为当前确定证据|回原件重提取，复算依赖结论与页面|
|新反例/工况边界|降低该范围适用状态，显示争议|收缩经验适用范围，保留失败证据及旧版本|

查询读取“发布快照＋当前失效水位”。发布快照解决复现，当前水位解决撤销/已知错误不能继续释放。入库检查和源变化检测有盲区时应如实声明检测时延；不能承诺尚未发现的外部变化已经生效。

反向依赖不完整时，保守标记相关主题/来源族待复核，不能因为没有记录边就宣布不受影响。影响遍历超预算输出未完成清单，持久化续跑；对已知撤销内容的阻断不等遍历完成，回源检查沿来源族ID即时约束。历史任务回执保留当时所用修订与后来失效提示，不改写成“当时已经知道”。

## 8. 任务查询：已积累理解与原始细节同时可达

普通主题问题用Wiki快速建立概念、条件和下一证据入口；精确标准号、符号、数值、句柄等同步走K1/K3，全域稀疏检索不等待Wiki。尚无页面、新资料未编译、长尾正文和冲突问题都能走原文路径。

运行步骤：

1. 固定作用域、知识发布代际与当前访问/失效水位。
2. 并行查主题页、精确项及原文全文，区分派生页候选和原始材料候选。
3. 由当前J缺口和D职责组装所需知识、例外及方法，展开支持链并按根来源去重。
4. 对精确引用/工程判断读取必要原件；纯概念综述可用已核不可变投影，但须明示本次未回读原文，不能计入原文读取指标。
5. 检查本图事实、对象绑定与条件；缺知识和缺本图事实分别报告。完成MethodRun后才能引用实际计算结果。
6. 返回证据、解释、未知与可验证改法。Wiki命中不等于证据充分；页面不存在也不等于知识库没有资料。

在既有QueryReceipt上设计扩展wiki_revision_ids、knowledge_revision_ids、dependency_manifest、invalidation_watermark、support_root_ids、source_read_states、compiled_coverage、uncompiled_scope、method_run_refs。字段须版本迁移后接入，不能假装现有0.2接口已经接受。

沿用03的Q0/Q1/Q2与读预算，不增加在线全库编译。Wiki构建耗时/成本归离线；查询首批证据、解释生成、图像识读和工程方法执行分别计时。过期Wiki可用于查找历史线索，作为当前判断证据前必须核对；来源撤销则按权限约束不释放内容。

## 9. 经验形成和采纳

经验通过“任务观测 → 解释假设 → 验证方案 → 方法/复检 → 有范围的复用”形成，可以退回、分支或证伪。阶段不是行政审批链，也不要求所有术语页走完工程验证。

- 观测：保存本图版本、对象/区域、问题、输入、执行和实际结果，包括失败。
- 假设：描述可能原因及可区分的替代解释，状态明确；聊天中说得有道理不足以验证。
- 验证：检查前提和反例，用相同工况的正常对照或独立材料验证；改法需要改后复检证据。
- 复用：只在验证范围内标SCOPED_VALIDATED；外推到新材料、设备、零件族、尺寸范围时重新检查。
- 修订：出现新反例或来源变化时收缩范围、标争议或撤销，保留过程。

阅读确认只确认字符或图面事实，不确认设计正确；一张图改好不等于形成通用工艺原则。十个由同一模板生成的样本不能当十次独立实践，专家意见也需记录身份来源、工况与确认范围，不凭页面署名制造独立核验。

一般解释和有据比较可自动作为候选综合积累；高影响工程要求必须经过对应来源、适用条件和方法验证才可执行。验证不必一律人工：可复算方法、约束检查和独立实物/案例证据均可按任务类型使用；模型互相赞同本身不构成工程验证。

## 10. 真实A样例的吸收方式与工艺样例模板

真实A01已有记录：原始识读为491.74cm，会诊怀疑应为mm，用户确认cm。此处仅复述[23真实反馈](23-真实人工反馈落盘与确认语义验证.md)中的历史证据，不在本轮重新识图。

应拆成：原图区域阅读主张、会诊推测、用户阅读确认、尚缺的设计工况/工程依据。Wiki可归纳“字符读取与工程合理性分别求证”的方法；不得写成“用户确认该设计合理”，也不得把原图统一改写为mm。其他样本没有相同证据时不能继承A01的确认。

手册工艺样例尚待资料到手，先明确产物模板：对象/加工特征 → 材料和设备/刀具/工序条件 → 来源推荐及表格/脚注 → 正常与不良对照 → 原因假设 → 可执行检查 → 改法与副作用 → 改后检验。没有正文、真实工况或检验结果的字段保持未知；不生成貌似成熟的老师傅经验。

## 11. 维护检查与自我强化风险

确定性检查：ID与引用有效、来源/页/框正确、hash和代际一致、重复/孤立页、条件/单位缺失、撤销传播、依赖循环、同根来源重复计数、页面与知识修订不一致。文本中的数值必须能对应原表/公式或有可复算推导，不能靠自然语言一致性通过。

模型辅助检查：概念遗漏、跨源矛盾、条件不一致、解释跳步、可能缺的反例与采购缺口。模型提出待查项，不能直接以“自检通过”修改核验状态。

问答回写保留问题和回答支持链，优先合并主题页或创建有价值比较，不把每条聊天都变成独立页面。避免循环：模型回答→Wiki→新回答→被当作多个来源；支持链必须追到外部原件/实际观测。压缩和汇总不能删除罕见条件、负例与未决项，其入口必须保留在目录或页内。

维护触发为材料到达、已知变更/撤销、任务出现新反例以及明确发起的检查批次。任务队列可由实施系统执行；本轮不创建或恢复用户已取消的定时跟进。
